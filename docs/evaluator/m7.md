# M7 핵심 실행 계획

목표는 **현재 프롬프트의 문제를 확인하고 가장 큰 문제 1~2개를 수정·재측정하는 것**이다. 하루 안에 필요한 평가 연결과 실제 비교에 집중한다. 완료 조건과 체크는 [plan.md](../../plan.md)의 M7 후속 항목을 따른다.

## 현재 상태와 다음 우선순위

5단계에서 최근 시도한 생성 프롬프트·평가기 변경은 사용자 요청으로 폐기하고 원복했다. 사용자가 추가한 Level 규칙 두 문장만으로 실험 1을 완료했다. LeetCode Senior는 0/3→1/3 Pass, 다른 세 대상의 Level 통과율은 같았고, 핵심인 Uber의 상위 개선 방향 차이는 남았다. 5·6단계는 미완료다. 폐기된 시도의 전후 수치를 현재 성과로 사용하지 않는다. [튜닝 기록의 현재 상태](tuning/golden-comparison-tuning.md)를 따른다.

골든셋 자체 품질 평가와 생성본 대 골든셋 비교는 별도다. 골든셋 자체의 high 반복 평가 평균은 Uber v3 98.77%, LeetCode v1 95.89%, YouTube 최종 v2 99.18%다. YouTube는 v2에서 95% 기준을 충족했으므로 중단하며, 추가 실험은 미채택으로 보존한다. 주제별 기록은 [Uber](tuning/golden-tuning.md), [LeetCode](tuning/leetcode-golden-tuning.md), [YouTube](tuning/youtube-golden-tuning.md)에 분리했다.

| 우선순위 | 작업 | 확인할 결과 |
| --- | --- | --- |
| 1 | 현재 변경을 증분별 커밋 | 검증된 기준선과 변경 이력 고정 |
| 2 | 기존 튜닝 주제의 Research 품질 개선 | Fetch 선별 평균 통과율 51.92%의 무관 문서·목록·중복과 핵심 근거 누락을 분석하고, 큰 원인부터 수정·동일 조건 재측정 |
| 3 | Keep → Selection → Rubric 영향 확인 | 바뀐 조사 결과로 후속 단계를 재실행·평가하고 하네스·Judge 회귀 확인 |
| 4 | 튜닝 주제의 생성본과 골든셋 비교·보완 | 핵심 NFR·설계 역량·0~3점 수준의 동등성을 비교하고 독립 루브릭 품질 점수와 분리 |
| 5 | 미사용 3~5개 주제로 전체 검증 | 우선 3주제의 Middle·Senior 전체 생성 6회에서 단계별 평가·골든 비교와 하네스·Judge 오탐·미탐 대조. 필요한 사례만 5주제로 확대 |

51.92%는 사람 정답 대비 정확도가 아니라 Research Fetch 선별 기준의 평균 통과율이다. Research 개선과 후속 골든 비교를 마치기 전에 여러 새 주제로 확대하지 않는다. 새 주제 결과를 보고 튜닝하면 해당 주제를 미사용 최종 검증으로 보고하지 않는다. 아래는 기존 M7 증분과 실행 규칙이며, 다음 실행 순서는 위 우선순위를 따른다. 생성·평가 추가 호출은 예산을 확인한 뒤 별도 실행한다.

## 작업 순서

| 순서 | 작업 | 실행 범위 |
| --- | --- | --- |
| 1 | 새 Research·Keep·Selection 기준 연결 | 기존 평가 코드와 저장·Langfuse 재사용, 최소 경계 검증 |
| 2 | 기존 Uber 기준선 평가 | Middle·Senior 저장 자료의 각 단계·기존 Rubric 품질 평가 각 1회 |
| 3 | 핵심 문제 1~2개만 튜닝 | 선택 단계·연차별 수정 전 2회, 수정 후 2회 실제 재실행 |
| 4 | 하네스·Judge 회귀 확인 | 기존 하네스 테스트·구조 오류 4사례 각 1회, Judge 의미 오류 2사례 각 2회 |
| 4b | 검출 튜닝 — 추가 요청 | 하네스 규칙 전후·Judge 프롬프트 전후 12회, 오류·정상 대조 분리 |
| 5 | 골든 비교 구현·튜닝 검증 | 사용자 골든 3세트 중 튜닝용 2주제에 적용 |
| 6 | 새 주제 전체 생성 반복 검증 | 5단계 완료 후, 사전 보류한 1주제로 연차별 3회·총 6회 새 생성 |

**골든 준비는 1~4의 선행 조건이 아니다.** Research·Keep·Selection은 해당 evaluator로, Rubric은 기존 품질 evaluator로 먼저 평가·튜닝한다. 골든 비교는 저장한 전후 산출물에 나중에 추가한다. 골든 준비가 늦어져도 앞 단계 결과를 기록하고 골든 관련 5·6단계를 미완료로 둔다.

## 튜닝의 최소 조건

- 생성·보완은 Sol medium, evaluator는 Sol high로 고정한다. 새 기준을 점수에 맞춰 수정하지 않는다.
- Keep은 같은 번호 있는 원문·예산, Selection은 같은 후보·보관 근거, Rubric은 같은 Research·Selection을 사용한다. Research는 같은 brief에서 새 조사하므로 검색 변동을 기록한다.
- Middle·Senior 전후 각 2회는 선택한 단계당 총 8회 단계 실행이다. 모든 단계를 전체 재조사 8회씩 하는 계획이 아니다. 한 번에 원인 하나만 수정하고 총 최대 두 시도로 제한한다.
- 실제 선택·생성을 다시 수행한다. 기존 출력 재채점은 프롬프트 튜닝 실험으로 세지 않는다. 평가기는 산출물당 1회 적용한다.
- 개선 미확인·명백한 회귀·치명적 신규 오류는 보류하거나 되돌린다. 사람 미검토 LLM 판단은 잠정값이며, 소수 실행의 점수 상승을 일반화 성능으로 표현하지 않는다.

## 골든 비교·튜닝

사용자 골든 **3주제 × Middle·Senior = 6개**를 사용한다. 튜닝용 2주제·최종 검증용 1주제는 출력 평가 전에 정하고 같은 주제의 두 연차를 함께 묶는다. 기존에 분석한 Uber는 튜닝용이다. 실제 파일이 준비되기 전에는 골든 완비로 표시하지 않는다.

`golden_comparison.md`로 NFR·핵심 설계 역량의 충족을 비교하고 `rubric.md`의 기존 품질 결과와 분리해서 저장한다. 기술·문장·배점의 일치를 강제하지 않는다. 대응 ID·근거·실제 누락과 자료 부족 null을 구분한다. Level 발전과 연차 적합성은 기존 Rubric Evaluator에 맡긴다. 골든 자체를 생성 결과에 맞춰 사후 수정하지 않는다.

이미 저장된 기준/후보 출력은 재사용한다. 5단계는 튜닝용 두 주제의 비교와 보완을 마치는 단계다. 사전에 최종 검증용으로 정한 세 번째 주제는 이 단계에서 평가하지 않는다.

## 골든 비교 이후: 새 주제 전체 생성 반복 검증

확정된 설정으로 미사용 주제의 Middle·Senior를 각각 3회, 총 6회 새로 생성한다. Research·Keep·Selection·Rubric과 하네스·렌더 검증을 실제 실행하고, 실험의 Judge 사용 여부를 고정한다. 모든 중간 산출물·Finding·보완·종료 상태를 저장하고 단계별 품질, 최종 Rubric 품질·골든 충족률·핵심 초점 누락·호출·시간·비용을 실행별로 기록한다.

이는 저장된 생성물 재평가·통제 오류 검출 실험과 별개다. 튜닝용 골든 비교 결과와 새 주제 결과를 합쳐 보고하지 않는다. 검증 결과를 보고 추가 튜닝하면 미사용 검증이라는 주장을 철회한다. 실제 호출 전 생성·평가 비용과 남은 시간을 확인하며, 전체 $30 잔여 또는 별도 승인 예산이 없으면 실행하지 않는다. 이 6회 검증으로 면접 전 범위를 닫는다.

## 결과 기록과 범위 제한

각 튜닝 문서에는 **문제·실패 근거 → 가설 → 실제 수정 → 고정 조건 → 실행별 전후 결과·Trace → 회귀·호출·시간·비용 → 채택/보류/되돌림**만 남긴다. 빈 실험 표·예상 개선 수치·예전 승인 대기 설명을 추가하지 않는다. 기존 실측값과 중단·실패 이력은 보존한다.

프롬프트를 바꾸면 문서에 **바뀐 부분의 수정 전·후 원문**을 나란히 남긴다. 전체 프롬프트 두 버전과 diff·해시는 실행 자료에 보존하고, 실행별 결과가 어느 버전을 사용했는지 연결한다. 수정 전후 점수만 기록하거나 원문을 덮어쓰지 않는다. 보류·되돌림한 후보도 같은 방식으로 남기며, 코드 수정 효과는 별도로 기록한다.

M7 전체 승인 예산은 $30 이내다. 2026-10-19 사용자 지시로 기존 $20에서 올렸다. 과거 사용량과 미확인 중단 호출의 과금을 고려해 실제 비용을 확인하며 진행하고 한도를 넘는 확대 실행은 하지 않는다. 생성 횟수와 API 호출 횟수는 다르다. 골든과 공통 품질 점수를 임의로 합치지 않는다.

이번에는 새 보고서 시스템·데이터셋 등록부·범용 로그 복원·대규모 라벨 수집·A~E 전면 반복을 구현하지 않는다. 기존 코드와 실험을 활용한다. README·일반 생성/TUI·운영 Judge 기본 설정은 변경하지 않는다.

새 세 기준 연결·테스트·기존 Uber 두 실행의 실제 기준선 평가와 하네스/Judge 최소 회귀 검사는 완료했다. Research 전후 각 4회(총 8회) 생성·평가를 완료하고 출처 규칙 한 항목을 잠정 채택했다. 전후 원문·diff·해시·실행별 결과·실패·비용을 Research 튜닝 문서에 기록했다. 골든 비교 구현과 기존 Uber 실제 기능 검증도 완료했다. 다른 두 주제의 골든은 아직 준비되지 않아 최종 3주제 검증은 미완료다.

### 골든 비교 수동 실행

```bash
python evaluate_rubric.py generated.md --golden resources/golden/uber/v3/uber_middle.md
```

생성물 1개와 같은 제목·범위·연차의 참조를 지정한다. 범위의 표현 차이는 의미로 확인한다. 반환값의 `quality`는 기존 품질 검사, `golden_comparison`은 NFR·핵심 설계 역량 충족률이며 각각 Trace를 가진다. 총점으로 합치지 않는다. 비교 기준의 미대응 Criterion 수와 자료 부족 `insufficient_data`는 별도로 기록한다. 이 옵션은 두 evaluator를 호출하므로 기존 품질 검사만 실행할 때보다 평가 호출이 추가된다. `--golden` 없는 기존 실행 방식은 유지한다.


## 이번 실행 결과

- 새 기준 연결·기준선 평가·Research 전후 실험 8회·하네스/Judge 회귀를 완료했다. Research 변경 원문과 실행별 결과는 [Research 튜닝 기록](tuning/research-tuning.md), Keep·Selection 기준선은 각 튜닝 문서에 기록했다.
- 출처 규칙 한 항목을 잠정 채택했다. 실행별 평균에서 Fetch 선별 31.20%→51.92%, 본문 유효성 79.24%→96.88%였고 Research 최종 후보의 핵심 초점 누락은 9건→1건이었다. 같은 Uber 한 주제의 관측이며 일반화 성능은 아니다.
- 골든 비교 구현과 기존 Uber 두 생성물의 실제 기능 검증은 완료했다. [Rubric 튜닝 기록](tuning/rubric-tuning.md)에 기존 품질과 골든 충족률의 차이를 분리했다. 다른 두 주제의 사용자 골든이 없어 튜닝된 산출물의 최종 3주제 비교·미사용 검증 주제 반복 생성은 미완료다. 기존 생성물의 기능 검증을 이 최종 검증으로 대체하지 않는다.
- 비 TUI fast 623개 통과, slow 2개 제외, 전체 Ruff lint 통과, 변경 파일 포맷과 diff 검사 통과다. 전체 포맷 검사에서는 이번 변경과 무관한 `test_catalog.py`, `test_nfr.py` 두 파일의 기존 차이가 남았다. TUI 실행 검증은 기존 시간 제한 종료 기록을 유지하며 완료로 표시하지 않는다.
- 확인된 완료 응답 146개의 누적 비용 추정은 $13.4067이다. 실패·중단 호출의 미확인 과금과 검색 요금은 제외하여 청구 총액으로 제시하지 않는다. 현재 예정된 API 작업은 모두 종료했다.
- 원본 실행 파일 72개와 사용자 평가 기준의 해시가 유지됐다. README·운영 Judge 기본값을 변경하지 않았고 커밋은 수행하지 않았다. 사용하지 않는 과거 6주제·5회 초안은 `.archgen/m7-followup/document-history/before-core-scope/m7-topics.json`에 보존했다.

추가 요청 4b의 검출 튜닝도 완료했다. 하네스의 정량 목표 검사 규칙은 통제 오류 검출 4/8→8/8·정상 대조 오탐 0/3으로 채택했다. Judge 후보 프롬프트는 전후 표적 검출 4/4·정상 대조 지적 0/2로 같아 되돌렸다. 원문·diff·입력·실행별 Trace·비용과 측정 한계는 [하네스·Judge 튜닝 기록](tuning/harness-judge-tuning.md)에 보존했다.

### 골든 비교 Evaluator 역할 재검증 (2026-10-19)

3-1을 삭제하고 타당한 대안을 인정한 기준으로 실험 1의 기존 4개를 각 1회 재평가했다. 골든 비교의 Fail 4건 중 LeetCode Senior 2건은 동일한 결과 지연 목표 누락이며 기존 Rubric 평가도 이미 발견했다. Uber 두 연차의 C1 Fail은 골든의 호출 전달 정책을 필수로 강제한 오판 의심으로 잠정 분류했다. 사람의 검토는 미완료이며 별도 비교기의 독립 신규 발견은 이번 표본에서 0개다. 원문·판정·에이전트 검토·기존 평가 대조는 [실험 2 기록](tuning/golden-coverage-recheck.md)에 있다. 새 생성·프롬프트 수정은 하지 않았다.

### YouTube 검증과 사용자 결정

현재 프롬프트로 YouTube Middle·Senior 각 1개를 실제 Research부터 생성했고 두 실행 모두 성공했다. 독립 Rubric 평가: Middle 40 Pass, Senior 39 Pass·1 Fail. 골든 v2 비교는 두 연차 각 8 Pass로 독립 신규 발견은 없었다. 상세 기록은 로컬 튜닝 문서 `youtube-coverage-comparison.md`에 있다. 사용자는 골든 비교기를 보류하고 튜닝 폴더를 Git 추적에서 제외하도록 지시했다. 비교기 코드·기존 결과는 보존하며 추가 비교 실행은 하지 않는다.
