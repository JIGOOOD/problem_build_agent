# Dropbox 파일 동기화

**설계 범위**
클라이언트의 파일 업로드·수정·삭제, 파일 내용과 버전 메타데이터 저장, 여러 기기의 변경 감지와 다운로드 동기화, 연결 중단 후 재개까지 설계한다. 문서 공동 편집·공개 링크 공유·파일 내용 검색은 제외한다.

**평가 초점**
중단된 대용량 파일 전송의 재개, 파일 내용과 버전 메타데이터의 일관성, 오프라인 및 동시 수정 충돌 처리, 많은 파일과 기기의 변경 탐지·동기화 부하 관리

**대상 연차** Senior\
**배점** 100

## NFR-1. Consistency

**요구 수준**
`consistency` — 완료된 것으로 관찰되는 버전은 그 버전에 대응하는 전체 내용을 조회할 수 있어야 하며, 누락되거나 검증에 실패한 내용을 정상 버전으로 공개하지 않는다. 전송 중 데이터의 선행 다운로드를 허용하더라도 완료된 버전과 구분한다.
완료된 파일 버전으로 공개되는 메타데이터는 실제로 확보된 해당 버전의 파일 내용과 일치해야 한다.

### C1. 파일 내용 확보와 버전 공개의 일관성 · 30

**평가 항목**
업로드·수정된 버전의 내용 확보와 메타데이터 공개 경계에서, 완료 버전이 검증된 전체 내용을 참조하도록 하는 확정 절차를 평가한다.

| Level | 기준 |
|---|---|
| 0 | 완료된 버전의 메타데이터와 실제 파일 내용이 불일치할 수 있는 문제를 고려하지 않는다. |
| 1 | 내용 저장소가 파일 내용을 확보하고 버전 관리 구성요소가 해당 내용과 검증 결과를 확인한 뒤 메타데이터를 공개하여, 다른 기기가 그 버전을 다운로드하는 기본 흐름을 설명한다. |
| 2 | 전체 내용의 존재와 무결성 확인을 버전 공개 조건으로 연결하는 구체적인 절차를 설명한다. 내용 누락·검증 실패나 저장과 공개 사이의 중단에도 불완전한 버전이 완료 상태로 노출되지 않도록 처리한다. |
| 3 | 2점 설계를 전제로, 내용 검증과 공개를 연결하는 방식이 어떤 조건에서 병목이나 복구 복잡성을 만드는지 분석하고, 대안의 처리 비용과 불완전 공개 위험을 비교하여 선택 근거를 설명한다. |

## NFR-2. Fault Tolerance

**요구 수준**
`fault_tolerance` — 재개 가능한 전송 상태가 유효한 동안 연결이 복구되면 확인된 완료 부분을 다시 보내지 않고 미완료 또는 실패한 부분부터 진행한다. 재개 결과가 원래 전송하려던 파일 버전과 일치하는지 확인한 뒤 완료로 처리한다.
파일 전송 중 연결이 끊겨도 이미 완료된 전송 부분을 재사용하여 안전하게 전송을 재개할 수 있어야 한다.

### C2. 완료 부분을 재사용하는 전송 재개 · 25

**평가 항목**
재개 상태가 유효한 업로드·다운로드에서 연결 복구 후 완료 부분을 재사용하고 원래 파일 버전과 일치하는 결과를 얻는 전송 복구 절차를 평가한다.

| Level | 기준 |
|---|---|
| 0 | 연결 중단 후 완료된 전송 부분을 식별하고 재사용하여 전송을 재개하는 문제를 고려하지 않는다. |
| 1 | 클라이언트와 전송 상대가 대상 버전 및 완료 부분의 기록을 이용해 미완료 부분을 이어 전송하고, 조립된 결과가 원래 버전과 일치하는지 확인하는 기본 흐름을 설명한다. |
| 2 | 재개 상태가 유효할 때 완료 부분을 판별해 재전송에서 제외하는 메커니즘을 설명한다. 응답 유실로 완료 여부가 불명확하거나 원본 파일이 변경된 경우에도 기록을 확인하고 버전을 구분하여 다른 내용이 섞이지 않게 처리한다. |
| 3 | 2점 설계를 전제로, 완료 기록의 세분화나 보존 방식이 어떤 조건에서 관리 비용 또는 재전송 비용을 키우는지 분석하고, 대안의 재사용 효율과 상태 관리 비용·위험을 비교하여 선택 근거를 설명한다. |

## NFR-3. Consistency

**요구 수준**
`consistency` — 연결이 복구되고 추가 변경이 멈춘 조건에서 각 기기는 조정된 파일 상태로 수렴한다. 같은 대상을 오프라인 또는 동시에 수정·삭제했을 때의 처리 규칙을 정의하고, 그 결과가 데이터 모델의 불변조건을 깨뜨리지 않도록 한다. 특정 충돌 사본 형식이나 모든 변경의 자동 병합은 강제하지 않는다.
오프라인 기기의 변경과 동시 변경은 재연결 후 정의된 충돌 처리 규칙에 따라 조정되어 유효한 파일 상태로 수렴해야 한다.

### C3. 오프라인·동시 변경의 충돌 조정과 수렴 · 25

**평가 항목**
연결 복구 후 필요한 전송이 가능하고 추가 변경이 멈춘 조건에서, 같은 파일의 수정·삭제 충돌을 조정하고 기기들이 유효한 상태로 수렴하는 절차를 평가한다.

| Level | 기준 |
|---|---|
| 0 | 오프라인 변경이나 동시 수정·삭제가 충돌할 때 결과를 조정하고 기기 간 상태를 수렴시키는 문제를 고려하지 않는다. |
| 1 | 클라이언트가 변경과 기준 버전을 전달하고 조정 구성요소가 수정·삭제 충돌을 판정해 정의된 규칙으로 결과를 정한 뒤, 각 기기가 그 결과를 적용하는 기본 흐름을 설명한다. |
| 2 | 기준 버전과 현재 상태를 비교하는 조건 및 수정·수정, 수정·삭제 충돌의 처리 방식을 구체화한다. 조정 중 다른 변경이 반영되면 판정을 갱신하고, 같은 조정 결과가 전파되어 삭제 상태 등 모델의 불변조건을 유지하며 수렴하도록 설명한다. |
| 3 | 2점 설계를 전제로, 선택한 충돌 규칙이 장기 오프라인이나 충돌 반복 시 어떤 결과와 한계를 만드는지 분석하고, 대안의 변경 보존 이점과 사용자 처리 부담 또는 조정 복잡성을 비교하여 선택 근거를 설명한다. |

## NFR-4. High Throughput

**요구 수준**
`throughput` — 변경 탐지에서 반복적인 전체 스캔 의존을 줄이고, 부하 제한 시 재시도가 요청량을 증폭시키지 않도록 한다. 동기화 작업과 임시 데이터의 증가를 제어하면서 대기 중인 변경 처리를 계속 진행할 수 있어야 한다. 구체적인 처리량과 허용 적체 시간은 부하 조건 확정 후 정한다.
많은 파일과 기기에서 변경 탐지·동기화 요청이 발생해도 불필요한 반복 조회와 재시도 증폭으로 유효한 변경 처리 능력이 소진되지 않아야 한다.

### C4. 변경 탐지와 동기화 부하 제어 · 20

**평가 항목**
많은 파일·기기의 변경 탐지와 동기화에서 반복 전체 조회, 재시도 증폭, 작업·임시 데이터 증가를 제어하면서 대기 변경 처리를 진행하는 설계를 평가한다.

| Level | 기준 |
|---|---|
| 0 | 반복 조회와 재시도 또는 동기화 작업의 누적이 유효한 변경 처리 능력을 소진할 수 있는 문제를 고려하지 않는다. |
| 1 | 변경 추적 구성요소가 전체 재조회 대신 필요한 변경을 찾아 작업으로 전달하고, 실행기가 동시 작업과 재시도를 조절하여 대기 변경을 처리하며 임시 데이터를 정리하는 기본 흐름을 설명한다. |
| 2 | 변경 진행 위치를 이용한 증분 탐지 또는 동등한 방식과 실행량·임시 데이터 제어를 구체화한다. 동시 재연결이나 부하 제한 시 유입·재시도를 지연 또는 제한하는 조건을 설명하고, 대기 변경은 후속 처리되도록 한다. |
| 3 | 2점 설계를 전제로, 변경 유입이 처리 능력을 넘거나 기기별 부하가 치우칠 때 적체와 자원 제한이 만드는 한계를 분석하고, 대안의 처리 효율과 지연·자원 비용을 비교하여 선택 근거를 설명한다. |
