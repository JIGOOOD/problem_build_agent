# Dropbox 파일 동기화

**설계 범위**
클라이언트의 파일 업로드·수정·삭제, 파일 내용과 버전 메타데이터 저장, 여러 기기의 변경 감지와 다운로드 동기화, 연결 중단 후 재개까지 설계한다. 문서 공동 편집·공개 링크 공유·파일 내용 검색은 제외한다.

**평가 초점**
중단된 대용량 파일 전송의 재개, 파일 내용과 버전 메타데이터의 일관성, 오프라인 및 동시 수정 충돌 처리, 많은 파일과 기기의 변경 탐지·동기화 부하 관리

**대상 연차** Middle\

## NFR-1. Consistency

**요구 수준**
`consistency` — 완료된 것으로 관찰되는 버전은 그 버전에 대응하는 전체 내용을 조회할 수 있어야 하며, 누락되거나 검증에 실패한 내용을 정상 버전으로 공개하지 않는다. 전송 중 데이터의 선행 다운로드를 허용하더라도 완료된 버전과 구분한다.
완료된 파일 버전으로 공개되는 메타데이터는 실제로 확보된 해당 버전의 파일 내용과 일치해야 한다.

### C1. 파일 내용과 완료 버전의 일치 · 30

**평가 항목**
업로드·수정된 버전의 전체 내용 확보와 검증을 완료 메타데이터 공개에 연결하는 설계를 평가하며, 전송 재개나 여러 변경 간 충돌 조정은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 완료 버전의 메타데이터가 실제 파일 내용과 일치해야 한다는 문제를 고려하지 않는다. |
| 1 | 내용 확보 후 버전을 공개하는 방향은 제시하지만, 내용 저장소와 메타데이터 관리의 역할 또는 검증과 공개의 연결 흐름이 불완전하다. |
| 2 | 내용 저장소와 버전 관리의 역할을 구분하고, 해당 버전의 전체 내용 확보와 무결성을 확인한 뒤 완료 메타데이터를 공개하여 다른 기기가 대응 내용을 조회하는 기본 흐름을 설명한다. |
| 3 | 2점 설계에 더해, 내용 저장과 버전 공개 사이의 중단 등 대표적인 문제를 설명하고, 미완료 상태의 구분이나 재확인 등 잘못된 완료 공개를 막는 기본 개선 방안을 제시한다. |

## NFR-2. Fault Tolerance

**요구 수준**
`fault_tolerance` — 재개 가능한 전송 상태가 유효한 동안 연결이 복구되면 확인된 완료 부분을 다시 보내지 않고 미완료 또는 실패한 부분부터 진행한다. 재개 결과가 원래 전송하려던 파일 버전과 일치하는지 확인한 뒤 완료로 처리한다.
파일 전송 중 연결이 끊겨도 이미 완료된 전송 부분을 재사용하여 안전하게 전송을 재개할 수 있어야 한다.

### C2. 중단된 파일 전송의 안전한 재개 · 25

**평가 항목**
업로드·다운로드에서 재개 상태가 유효한 동안 연결 복구 후 완료 부분을 재사용하고 원래 전송 버전을 확인하는 흐름을 평가하며, 완료 메타데이터 공개 판단은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 연결 중단 후 완료된 전송 부분을 재사용하여 전송을 재개하는 문제를 고려하지 않는다. |
| 1 | 부분 전송 기록이나 이어받기를 제안하지만, 완료 부분을 식별하는 방식 또는 기록을 이용해 미완료 부분을 전송하는 흐름이 불완전하다. |
| 2 | 클라이언트와 전송 상대가 파일 버전 및 완료 부분을 기록·확인하는 역할을 설명하고, 유효한 재개 상태로 확인된 부분은 다시 보내지 않으며 나머지를 전송한 뒤 원래 버전과의 일치를 검증하는 흐름을 제시한다. |
| 3 | 2점 설계에 더해, 중단 중 원본 변경이나 완료 기록 불일치 같은 대표적인 한계를 설명하고, 버전 재확인이나 불확실한 부분의 재검증 등 안전한 재개를 위한 기본 개선 방안을 제시한다. |

## NFR-3. Consistency

**요구 수준**
`consistency` — 연결이 복구되고 추가 변경이 멈춘 조건에서 각 기기는 조정된 파일 상태로 수렴한다. 같은 대상을 오프라인 또는 동시에 수정·삭제했을 때의 처리 규칙을 정의하고, 그 결과가 데이터 모델의 불변조건을 깨뜨리지 않도록 한다. 특정 충돌 사본 형식이나 모든 변경의 자동 병합은 강제하지 않는다.
오프라인 기기의 변경과 동시 변경은 재연결 후 정의된 충돌 처리 규칙에 따라 조정되어 유효한 파일 상태로 수렴해야 한다.

### C3. 오프라인·동시 변경의 충돌 조정 · 25

**평가 항목**
같은 파일의 오프라인·동시 수정과 삭제를 조정하고, 연결 복구 후 필요한 전송이 가능하며 추가 변경이 멈춘 조건에서 기기들이 수렴하는 흐름을 평가한다.

| Level | 기준 |
|---|---|
| 0 | 오프라인 변경이나 여러 기기의 수정·삭제가 충돌할 수 있다는 문제를 고려하지 않는다. |
| 1 | 충돌을 인식하고 우선순위나 충돌 사본 등의 해결 방향을 제시하지만, 변경 기준을 비교하는 역할이나 조정 결과를 기기에 반영하는 흐름이 불완전하다. |
| 2 | 기기에 보관한 변경과 기준 버전을 서버 상태와 비교하여 충돌을 판정하고, 수정 간 및 수정·삭제 간 처리 규칙을 적용해 유효한 결과를 각 기기에 전파하는 기본 흐름으로 명시된 조건에서의 수렴을 설명한다. |
| 3 | 2점 설계에 더해, 오래된 수정이 삭제 결과를 되살리는 경우 등 선택한 조정 규칙의 대표적인 문제를 설명하고, 삭제 이력이나 기준 버전 확인 등 일관된 결과를 유지하는 기본 개선 방안을 제시한다. |

## NFR-4. High Throughput

**요구 수준**
`throughput` — 변경 탐지에서 반복적인 전체 스캔 의존을 줄이고, 부하 제한 시 재시도가 요청량을 증폭시키지 않도록 한다. 동기화 작업과 임시 데이터의 증가를 제어하면서 대기 중인 변경 처리를 계속 진행할 수 있어야 한다. 구체적인 처리량과 허용 적체 시간은 부하 조건 확정 후 정한다.
많은 파일과 기기에서 변경 탐지·동기화 요청이 발생해도 불필요한 반복 조회와 재시도 증폭으로 유효한 변경 처리 능력이 소진되지 않아야 한다.

### C4. 변경 탐지와 동기화 부하 제어 · 20

**평가 항목**
많은 파일·기기의 변경 탐지부터 대기 작업 처리까지 반복 조회, 재시도 및 임시 데이터 증가를 제어하는 설계를 평가하며, 미확정 처리량이나 지연 수치는 요구하지 않는다.

| Level | 기준 |
|---|---|
| 0 | 반복적인 전체 조회나 제어되지 않은 동기화 요청이 유효한 변경 처리를 소진할 수 있다는 문제를 고려하지 않는다. |
| 1 | 증분 탐지나 작업량 제한 등의 방향을 제시하지만, 변경 탐지 결과가 대기 작업과 실행 제어로 이어지는 구성요소의 역할이나 처리 흐름이 불완전하다. |
| 2 | 변경 이력이나 동등한 방식으로 전체 재조회를 줄이고, 대기 작업을 제한된 실행량으로 처리하는 흐름을 설명한다. 부하 제한 시 재시도를 늦추고 임시 데이터를 정리하여 대기 변경 처리를 이어가는 기본 방식을 제시한다. |
| 3 | 2점 설계에 더해, 동시 재연결로 대기 작업이 몰리는 경우 등 대표적인 병목이나 한계를 설명하고, 재시도 분산이나 작업 묶음 조정 등 유효한 변경 처리를 유지하는 기본 개선 방안을 제시한다. |
