# Slack 채널 메시징

**설계 범위**
워크스페이스의 채널에서 텍스트 메시지 전송·저장·실시간 전달, 메시지 이력 조회와 연결 중단 후 누락 메시지 동기화까지 설계한다. 검색·파일 첨부·음성 및 영상 통화는 제외한다.

**평가 초점**
접수된 메시지의 유실 방지, 재시도·재접속 시 중복과 채널 내 순서 처리, 온라인 수신자의 메시지 전달 지연, 대규모 채널의 메시지 전달 부하 분산

**대상 연차** Senior\
**배점** 100

## NFR-1. Fault Tolerance

**요구 수준**
`fault_tolerance` — 접수 성공으로 확정한 메시지가 합의한 장애 후에도 이력에 남아야 한다. 실시간 전달 누락은 재접속 후 이력과 대조하여 복구할 수 있어야 하며, 처리 결과가 불확실한 요청은 성공으로 단정하지 않고 안전하게 재확인하거나 재시도할 수 있어야 한다.
성공적으로 접수한 메시지는 합의한 장애 범위에서 유실되지 않으며, 연결 중단으로 실시간 전달을 놓친 메시지는 저장된 이력으로 복구할 수 있어야 한다.

### C1. 접수 메시지 보존과 누락 복구 · 30

**평가 항목**
합의한 장애 범위와 이력 보존 범위 안에서 접수 성공의 확정 조건, 메시지 영속화, 연결 중단 후 누락 메시지 복구 경로를 평가하며 중복 반영과 순서 판단은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 접수 성공한 메시지의 장애 후 보존과 연결 중단으로 놓친 메시지의 복구를 설계에서 고려하지 않는다. |
| 1 | 접수 성공 시점과 보장할 장애 범위를 정하고, 저장 담당 구성요소의 영속화 확인에서 성공 응답까지의 흐름과 재접속 후 저장 이력을 읽어 누락 메시지를 복구하는 흐름을 설명한다. |
| 2 | 영속화 완료 판정 조건과 장애 후 기록 복구 방식을 구체화한다. 저장 후 응답 유실 등 결과가 불확실한 요청의 재확인·재시도 처리와, 합의한 보존 범위에서 복구 위치를 기준으로 누락 이력을 읽는 동작을 설명한다. |
| 3 | 2점 설계를 전제로, 장애 시점과 보존 구성에 따라 보장 범위가 제한되는 이유를 분석한다. 성공 확정 조건이나 보존 방식의 대안을 비교하고, 내구성 강화와 저장·복제 대기 비용 사이의 선택 근거를 설명한다. |

## NFR-2. Consistency

**요구 수준**
`consistency` — 동시 전송된 메시지에 채널별로 일관된 확정 순서를 부여하고, 실시간 수신과 이력 조회가 같은 메시지 집합과 순서로 수렴해야 한다. 응답 유실에 따른 재시도와 재접속 시 조회 구간 중첩이 사용자에게 중복 메시지로 남지 않아야 한다.
같은 채널의 확정된 메시지는 사용자와 조회 경로 사이에서 일관된 순서로 관찰되어야 하며, 재시도와 재접속 동기화가 같은 메시지를 별개의 메시지로 중복 반영하지 않아야 한다.

### C2. 채널 순서와 중복 없는 반영 · 30

**평가 항목**
같은 채널에서 동시 전송의 확정 순서, 재시도의 메시지 식별, 재접속 시 이력과 실시간 수신의 병합을 평가하며 채널 간 전역 순서나 즉시 최신성은 요구하지 않는다.

| Level | 기준 |
|---|---|
| 0 | 채널 내 확정 순서의 일관성과 재시도·재접속으로 같은 메시지가 중복 반영되는 문제를 설계에서 고려하지 않는다. |
| 1 | 채널별 순서를 정하는 역할과 메시지를 식별하는 방법을 정하고, 재시도를 기존 메시지에 연결하며 이력과 실시간 수신을 같은 식별값·순서 기준으로 합쳐 사용자에게 반영하는 기본 흐름을 설명한다. |
| 2 | 동시 전송의 순서 확정과 동일 요청의 중복 생성 방지 조건을 구체화한다. 응답 유실 후 재시도와 재접속 중 이력·실시간 구간 중첩을 처리하여, 수신 순서가 달라도 중복 없이 같은 확정 순서로 수렴하는 메커니즘을 설명한다. |
| 3 | 2점 설계를 전제로, 순서 확정의 집중이나 병렬 전달의 재정렬 부담이 어떤 조건에서 한계가 되는지 분석한다. 순서를 유지하는 분할과 수신 측 재정렬 등 대안의 이점·상태 관리 비용·위험을 비교하여 선택 근거를 설명한다. |

## NFR-3. Low Latency

**요구 수준**
`latency` — 송신 요청부터 정상 연결된 온라인 수신자의 수신까지 측정 구간을 명시하고, 저장·큐잉·팬아웃 과정의 대기로 실시간 대화가 장시간 정체되지 않도록 해야 한다. 백분위와 부하별 수치 기준은 별도 합의가 필요하다.
온라인 수신자는 채널 메시지를 대화에 적합한 낮은 지연으로 전달받아야 한다.

### C3. 온라인 전달 지연 관리 · 20

**평가 항목**
명시한 온라인 전달 대상과 구독 정책 아래 송신 요청부터 정상 연결된 수신자의 수신까지 저장·큐잉·팬아웃의 대기와 지연 제어를 평가하며 미합의 수치 목표는 요구하지 않는다.

| Level | 기준 |
|---|---|
| 0 | 온라인 수신자에게 도달하는 전달 경로의 지연과 대기 발생 구간을 설계에서 고려하지 않는다. |
| 1 | 온라인 전달 대상과 측정 시작·종료 지점을 정하고, 저장 확인·전달 대기열·연결 담당 구성요소의 역할을 연결하여 메시지가 수신자에게 전달되는 흐름과 지연을 줄이는 기본 방식을 설명한다. |
| 2 | 저장·큐잉·팬아웃의 지연을 구분해 관측하고, 대기 증가 시 제어가 작동하는 조건과 처리 방식을 설명한다. 느린 수신자나 전달 적체 등 해당 경로의 주요 병목이 다른 정상 수신자의 전달을 장시간 막지 않도록 대응한다. |
| 3 | 2점 설계를 전제로, 저장 대기나 전달 적체가 어떤 부하 조건에서 지연을 지배하는지 분석한다. 병렬화·묶음 처리·대기열 분리 등 관련 대안의 지연 개선과 자원 비용 또는 위험을 비교하고, 보존·순서 요구를 유지하는 선택 근거를 설명한다. |

## NFR-4. Scalability

**요구 수준**
`scalability` — 온라인 수신자와 메시지 유입이 증가하면 전달 작업을 추가 자원에 분산할 수 있어야 한다. 단일 대규모 채널이 하나의 전달 처리 주체에 묶이지 않아야 하며, 확장 과정에서도 메시지 복구와 채널 순서 요구를 유지해야 한다.
채널 수와 온라인 수신자 수가 늘어날 때 전달 용량을 확장할 수 있어야 하며, 단일 대규모 채널의 팬아웃도 여러 처리 주체로 분산할 수 있어야 한다.

### C4. 대규모 채널의 전달 작업 분산 · 20

**평가 항목**
채널 수와 온라인 수신자 증가에 따른 전달 작업·상태의 배치 및 단일 대규모 채널 내부의 확장을 평가하며 복구와 순서는 확장 시 유지할 제약으로만 다룬다.

| Level | 기준 |
|---|---|
| 0 | 채널 수나 온라인 수신자 증가에 따른 전달 용량 확장과 단일 대규모 채널의 팬아웃 분산을 설계에서 고려하지 않는다. |
| 1 | 채널 간 작업 배치와 단일 채널 내부의 수신자별 전달 분담을 설명한다. 메시지가 여러 전달 담당으로 나뉘고 각 담당이 맡은 연결로 전송하는 흐름을 통해 추가 자원으로 전달 작업을 분산한다. |
| 2 | 작업 분할 기준과 수신자·구독 상태 배치를 구체화하고, 인기 채널의 작업 집중이나 자원 추가 시 담당 변경을 처리하는 조건과 방식을 설명한다. 단순히 채널 수만 나누지 않고 채널 내부를 확장하며 기존 복구·순서 요구를 유지한다. |
| 3 | 2점 설계를 전제로, 수신자 증가에 따른 전달량이나 상태 복제·재배치가 확장을 제한하는 조건과 이유를 분석한다. 분할 단위나 중계·상태 배치 대안의 분산 효과와 통신·메모리 비용 또는 순서 유지 위험을 비교하여 선택 근거를 설명한다. |
