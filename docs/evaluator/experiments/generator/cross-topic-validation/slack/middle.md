# Slack 채널 메시징

**설계 범위**
워크스페이스의 채널에서 텍스트 메시지 전송·저장·실시간 전달, 메시지 이력 조회와 연결 중단 후 누락 메시지 동기화까지 설계한다. 검색·파일 첨부·음성 및 영상 통화는 제외한다.

**평가 초점**
접수된 메시지의 유실 방지, 재시도·재접속 시 중복과 채널 내 순서 처리, 온라인 수신자의 메시지 전달 지연, 대규모 채널의 메시지 전달 부하 분산

**대상 연차** Middle\
**배점** 100

## NFR-1. Fault Tolerance

**요구 수준**
`fault_tolerance` — 접수 성공으로 확정한 메시지가 합의한 장애 후에도 이력에 남아야 한다. 실시간 전달 누락은 재접속 후 이력과 대조하여 복구할 수 있어야 하며, 처리 결과가 불확실한 요청은 성공으로 단정하지 않고 안전하게 재확인하거나 재시도할 수 있어야 한다.
성공적으로 접수한 메시지는 합의한 장애 범위에서 유실되지 않으며, 연결 중단으로 실시간 전달을 놓친 메시지는 저장된 이력으로 복구할 수 있어야 한다.

### C1. 접수 메시지 보존과 누락 복구 · 30

**평가 항목**
합의한 장애 범위에서 접수 성공을 확정하는 조건과 저장 경로, 합의한 이력 보존 범위 안에서 재접속 후 누락 메시지를 복구하는 흐름을 평가하며 중복 반영과 순서 판단은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 접수 성공한 메시지의 보존 조건과 연결 중단으로 놓친 메시지의 복구 경로를 고려하지 않는다. |
| 1 | 메시지 유실과 누락 복구 문제를 인식하고 영속 저장이나 이력 재조회를 제안하지만, 성공 응답과 저장 완료의 관계 또는 재접속 복구 흐름을 충분히 설명하지 못한다. |
| 2 | 접수 성공 시점과 보장할 장애 범위를 명시하고, 그 범위에서 메시지를 보존하는 저장 구성요소의 역할을 설명한다. 결과가 불확실하면 성공으로 단정하지 않으며, 재접속 시 마지막 수신 지점 이후를 보존된 이력에서 복구하는 기본 흐름을 연결한다. |
| 3 | 2점 설계에 더해, 저장 완료 후 응답이 끊기거나 이력 복구 도중 연결이 다시 끊기는 등 대표적인 문제를 설명하고, 결과 재확인이나 복구 진행 지점 유지와 같은 기본 개선 방안을 제시한다. |

## NFR-2. Consistency

**요구 수준**
`consistency` — 동시 전송된 메시지에 채널별로 일관된 확정 순서를 부여하고, 실시간 수신과 이력 조회가 같은 메시지 집합과 순서로 수렴해야 한다. 응답 유실에 따른 재시도와 재접속 시 조회 구간 중첩이 사용자에게 중복 메시지로 남지 않아야 한다.
같은 채널의 확정된 메시지는 사용자와 조회 경로 사이에서 일관된 순서로 관찰되어야 하며, 재시도와 재접속 동기화가 같은 메시지를 별개의 메시지로 중복 반영하지 않아야 한다.

### C2. 채널별 확정 순서와 중복 반영 방지 · 30

**평가 항목**
같은 채널의 확정 순서를 실시간 수신과 이력 조회에 일관되게 적용하고 재시도·재접속의 중복 반영을 막는 식별 및 병합 흐름을 평가하며 저장 내구성과 복구 가능 여부는 제외한다.

| Level | 기준 |
|---|---|
| 0 | 채널별 메시지 순서의 일관성과 재시도·재접속으로 같은 메시지가 중복 반영되는 문제를 고려하지 않는다. |
| 1 | 채널 순서와 중복 문제를 인식하고 순서값이나 식별값 사용을 제안하지만, 값을 결정하는 주체 또는 재시도와 이력·실시간 수신을 연결하는 처리 흐름이 불완전하다. |
| 2 | 동시 전송에도 채널별 확정 순서를 정하는 주체와 기준을 설명한다. 재시도를 같은 요청으로 식별하고, 이력과 실시간 수신을 동일한 메시지 식별·정렬 기준으로 병합하여 사용자에게 중복 없이 같은 순서로 수렴시키는 기본 흐름을 제시한다. |
| 3 | 2점 설계에 더해, 병렬 전달로 도착 순서가 달라지거나 재접속 조회와 실시간 수신이 겹치는 대표적인 문제를 설명하고, 확정 순서에 따른 재정렬이나 중복 판정 상태 유지 등 기본 개선 방안을 제시한다. |

## NFR-3. Low Latency

**요구 수준**
`latency` — 송신 요청부터 정상 연결된 온라인 수신자의 수신까지 측정 구간을 명시하고, 저장·큐잉·팬아웃 과정의 대기로 실시간 대화가 장시간 정체되지 않도록 해야 한다. 백분위와 부하별 수치 기준은 별도 합의가 필요하다.
온라인 수신자는 채널 메시지를 대화에 적합한 낮은 지연으로 전달받아야 한다.

### C3. 온라인 메시지 전달 지연 · 20

**평가 항목**
명시한 온라인 전달 대상에 대해 송신 요청부터 수신까지의 측정 구간과 저장·큐잉·전달 경로의 대기 축소를 평가하며 전달 용량의 분할·증설 방식 자체는 제외한다.

| Level | 기준 |
|---|---|
| 0 | 온라인 수신자에게 메시지가 도달하기까지의 지연이나 전달 경로에서 발생하는 대기를 고려하지 않는다. |
| 1 | 낮은 전달 지연의 필요성을 인식하고 지속 연결이나 비동기 처리를 제안하지만, 온라인 전달 대상과 측정 구간 또는 저장부터 수신까지의 주요 처리 흐름을 충분히 설명하지 못한다. |
| 2 | 온라인 전달 대상과 구독 정책, 송신 요청부터 정상 연결된 수신자의 수신까지의 측정 구간을 명시한다. 저장·큐·전달 구성요소의 역할과 흐름을 설명하고, 보존 요구를 유지하면서 불필요한 대기나 주기적 조회 없이 전달하는 기본 경로를 제시한다. |
| 3 | 2점 설계에 더해, 저장 확인 대기나 전달 큐 적체 등 대표적인 지연 원인을 짚고 구간별 관측과 기본 개선 방안을 설명한다. 저장 대기를 줄일 때도 접수 메시지의 보존 요구를 훼손하지 않는 방향을 제시한다. |

## NFR-4. Scalability

**요구 수준**
`scalability` — 온라인 수신자와 메시지 유입이 증가하면 전달 작업을 추가 자원에 분산할 수 있어야 한다. 단일 대규모 채널이 하나의 전달 처리 주체에 묶이지 않아야 하며, 확장 과정에서도 메시지 복구와 채널 순서 요구를 유지해야 한다.
채널 수와 온라인 수신자 수가 늘어날 때 전달 용량을 확장할 수 있어야 하며, 단일 대규모 채널의 팬아웃도 여러 처리 주체로 분산할 수 있어야 한다.

### C4. 채널 및 수신자 증가에 따른 전달 분산 · 20

**평가 항목**
채널 간 작업 배치와 단일 대규모 채널 내부의 수신자 전달 작업을 추가 자원에 분산하는 구조를 평가하며 순서·복구 메커니즘과 전달 지연 자체는 별도 채점하지 않는다.

| Level | 기준 |
|---|---|
| 0 | 채널 수와 온라인 수신자가 늘어날 때의 전달 용량 확장 및 단일 대규모 채널의 작업 분산을 고려하지 않는다. |
| 1 | 전달 부하 증가를 인식하고 서버 증설이나 채널 분할을 제안하지만, 단일 대규모 채널의 전달 작업을 여러 처리 주체에 나누는 역할과 흐름을 충분히 설명하지 못한다. |
| 2 | 채널 간 작업 배치와 단일 대규모 채널의 수신자별 전달 작업 분산을 설명한다. 구독 정보에 따라 여러 처리 주체가 맡은 수신자에게 전달하고 자원 추가 시 작업을 나누는 기본 흐름을 제시하며, 기존 순서·복구 경로를 유지하도록 연결한다. |
| 3 | 2점 설계에 더해, 수신자 편중으로 일부 전달 주체에 부하가 몰리거나 구독 상태의 과도한 복제가 확장을 막는 대표적인 한계를 설명하고, 작업 재분배나 필요한 상태만 배치하는 기본 개선 방안을 제시한다. |
