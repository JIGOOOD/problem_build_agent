# 공연 좌석 티켓 예매

**설계 범위**
공연별 좌석 잔여 현황 조회, 좌석 임시 점유와 만료, 주문 생성과 외부 결제 결과에 따른 예매 확정 또는 해제까지 설계한다. 결제 대행사 내부 구현·환불·재판매·공연 추천은 제외한다.

**평가 초점**
동일 좌석의 중복 예매 방지, 점유 만료·지연 결제 응답·재시도의 상태 일관성, 예매 오픈 시 조회·점유 요청 폭증 대응, 접수된 주문의 장애 후 복구와 중복 확정 방지

**대상 연차** Middle\
**배점** 100

## NFR-1. Consistency

**요구 수준**
`consistency` — 동시 요청에서도 같은 좌석에 서로 충돌하는 점유나 예매를 성공시키지 않는다. 지연 결제 응답과 오래된 만료 작업은 현재 소유권과 확정 상태를 덮어쓰지 않는다. 조회에 보인 잔여 좌석은 점유 성공을 보장하지 않으며, 실제 점유·확정 시 유효성을 판정한다.
동일 공연의 동일 좌석에는 유효한 점유 소유자와 확정 예매가 충돌하지 않아야 하며, 점유·만료·결제 결과·재시도의 경합에서도 허용된 상태 전이만 반영되어야 한다.

### C1. 좌석 소유권과 상태 전이의 정합성 · 30

**평가 항목**
조회부터 점유·만료·결제 결과 반영까지 좌석 소유권과 유효성을 판정하는 흐름을 평가하며, 장애 후 주문 복구가 아닌 동시 요청과 지연 작업 사이의 상태 전이 규칙을 다룬다.

| Level | 기준 |
|---|---|
| 0 | 동일 좌석에 여러 점유나 예매가 함께 성공할 수 있는 문제를 고려하지 않고, 좌석 상태를 읽고 변경하는 흐름만 제시한다. |
| 1 | 중복 예매 위험을 인식하고 잠금이나 상태 검사 등의 방안을 제시하지만, 소유권·만료·결제 결과가 충돌할 때 무엇을 확인하고 반영하는지 충분히 설명하지 못한다. |
| 2 | 조회 결과와 실제 점유 판정을 구분하고, 상태 변경을 판정하는 컴포넌트의 역할을 설명한다. 소유권과 유효성을 확인하여 점유·만료·결제 결과·재시도에 허용된 전이만 반영하는 기본 흐름과 경합 정책을 제시한다. |
| 3 | 2점 설계에 더해, 작업 시작 때 확인한 상태가 실행 시점에는 달라질 수 있음을 설명한다. 오래된 만료 작업이나 지연 결제 응답이 현재 소유권과 확정 상태를 덮어쓰지 않도록 반영 시 재검증하는 등의 개선을 제시한다. |

## NFR-2. Fault Tolerance

**요구 수준**
`fault_tolerance` — 주문 접수를 성공으로 응답한 뒤 처리 프로세스가 중단되어도 주문과 처리 진행 상태를 복구할 수 있다. 동일 요청이나 결제 이벤트를 다시 처리해도 예매 확정 효과는 중복되지 않는다. 결제 결과를 받지 못했거나 점유 만료와 충돌한 주문은 확인 가능한 미결 상태로 남겨 외부 상태와 대사하며, 이미 재할당된 좌석을 중복 확정하지 않는다.
접수한 주문은 처리 중 장애와 외부 결제 결과의 유실·중복 전달 이후에도 복구 가능해야 하며, 복구와 재시도가 중복 주문 효과나 중복 예매 확정을 만들지 않아야 한다.

### C2. 접수 주문의 복구와 중복 효과 방지 · 25

**평가 항목**
주문 접수 성공 이후의 처리 중단과 외부 결제 결과 유실·중복에 대해, 좌석 전이 정책 자체가 아닌 진행 상태 보존·재처리·대사 흐름을 평가한다.

| Level | 기준 |
|---|---|
| 0 | 접수 성공 이후 프로세스 중단이나 결제 결과 유실로 주문 처리가 사라질 수 있는 문제와, 재처리로 효과가 중복될 수 있는 문제를 고려하지 않는다. |
| 1 | 주문 저장과 재시도가 필요함을 인식하고 기본 방안을 제시하지만, 접수 응답과 저장의 순서, 복구할 작업의 식별 또는 중복 반영 방지 흐름을 충분히 설명하지 못한다. |
| 2 | 접수 성공 전에 주문과 복구에 필요한 진행 상태를 보존하고, 중단된 작업을 찾아 재처리하는 컴포넌트와 흐름을 설명한다. 동일 요청·결제 이벤트의 중복 효과를 막고, 불확실한 주문을 미결로 추적하여 외부 상태와 대사한다. |
| 3 | 2점 설계에 더해, 재처리 도중 다시 중단되거나 결제 결과가 계속 전달되지 않는 한계를 설명한다. 처리 기록과 실제 반영 결과를 함께 확인하거나 외부 상태를 재조회하는 등, 중복 확정 없이 복구를 이어갈 개선을 제시한다. |

## NFR-3. High Throughput

**요구 수준**
`throughput` — 검증된 처리 능력에 맞추어 유입을 제어하고, 초과 요청은 대기 또는 명시적인 제한 응답으로 처리한다. 요청 폭증이 내부 작업의 무제한 적체나 전체 처리 실패로 이어지지 않도록 하며, 이미 진입한 요청의 처리를 지속할 수 있어야 한다. 구체적인 처리량과 동시 사용자 한도는 부하 검증으로 정한다.
예매 오픈 시 요청 유입이 처리 능력을 넘더라도 실제 처리 경로에 전달되는 부하를 제어하여, 접수한 조회·점유·주문 처리가 과부하로 함께 붕괴하지 않아야 한다.

### C3. 폭증 유입 제어와 접수 작업 보호 · 25

**평가 항목**
예매 오픈 시 조회·점유·주문 요청이 처리 능력을 초과하는 경우의 유입 제어와 내부 적체 제한을 평가하며, 자원 추가에 따른 처리 범위 확장은 별도로 다룬다.

| Level | 기준 |
|---|---|
| 0 | 요청 유입이 처리 능력을 넘는 상황을 고려하지 않고, 들어오는 요청을 제한 없이 내부 처리 경로로 전달한다. |
| 1 | 폭증에 대한 대기나 제한이 필요함을 인식하지만, 제어 위치와 초과 요청의 처리 방식 또는 이미 접수한 작업을 계속 진행시키는 흐름을 충분히 설명하지 못한다. |
| 2 | 부하 검증으로 수용 한계를 정하고, 그에 맞춰 유입을 제어하는 컴포넌트와 흐름을 설명한다. 초과 요청은 대기나 명시적 제한으로 처리하고, 내부 적체를 제한하여 이미 접수한 조회·점유·주문 처리가 계속 진행되도록 설계한다. |
| 3 | 2점 설계에 더해, 고정된 유입 한도가 실제 처리 능력의 변화나 적체 증가를 반영하지 못하는 한계를 설명한다. 처리 완료량과 적체 상태 등을 관찰해 유입이나 대기 수용 범위를 조정하는 개선을 제시한다. |

## NFR-4. Scalability

**요구 수준**
`scalability` — 공연 수와 요청량 증가에 따라 처리 자원을 추가해 수용 범위를 넓힐 수 있어야 한다. 인기 공연에 부하가 집중되는 경우에도 추가 자원이 효과를 내는 분산 단위와 남는 병목을 설명하고 검증할 수 있어야 한다. 동일 좌석의 충돌 판정을 병렬화한다는 이유로 정합성을 약화하지 않는다.
조회·점유 부하가 증가할 때 자원과 처리 범위를 확장할 수 있어야 하며, 특정 인기 공연에 집중된 부하가 하나의 고정된 처리 단위에만 묶이지 않도록 해야 한다.

### C4. 부하 분산 단위와 확장 경계 · 20

**평가 항목**
공연 수와 조회·점유 부하 증가에 따른 자원 확장 및 인기 공연 내부의 분산 단위를 평가하며, 유입 제한이나 좌석 전이 규칙 자체가 아닌 추가 자원의 활용 범위와 병목을 다룬다.

| Level | 기준 |
|---|---|
| 0 | 공연 수나 요청량 증가에 따라 처리 범위를 넓혀야 하는 문제를 고려하지 않고, 고정된 처리 자원과 단일 경로만 제시한다. |
| 1 | 자원 추가나 분산을 제시하지만, 조회·점유 요청이 추가 자원으로 어떻게 나뉘는지 또는 인기 공연의 부하가 어디에 집중되는지 충분히 설명하지 못한다. |
| 2 | 조회와 점유의 접근 경로에 맞춰 자원 추가와 요청 분산의 기본 흐름을 설명한다. 인기 공연 내부에서도 부하를 나눌 단위를 제시하고, 동일 좌석의 충돌 판정을 유지하면서 추가 자원의 효과와 남는 병목을 부하 검증으로 확인하는 방안을 설명한다. |
| 3 | 2점 설계에 더해, 선택한 분산 단위에서도 일부 좌석이나 공통 처리 지점으로 부하가 쏠릴 수 있음을 설명한다. 분산 단위 조정이나 공통 경로의 부하 감소 등 개선을 제시하고, 동일 좌석의 경합처럼 자원 추가만으로 줄지 않는 한계를 구분한다. |
