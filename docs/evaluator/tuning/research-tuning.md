# Research 튜닝 기록

## 평가 범위와 현재 결론

2026년 10월 19일 Uber의 Middle·Senior를 진단한 뒤, 실험 1에서 초기 검색 프롬프트를 전후 8회 비교하고 실험 2에서 도구 프롬프트·선택 Fetch 코드를 새 실행 4회로 검증했다. 각 실험의 1~6 전체 판정과 모든 Fail·판단 불가를 실행별 상세 표에 보존한다.

**현재 결과:** 실험 2의 4-1 평균 통과율은 **51.92% → 100%**, 선택한 문서는 **38/38 Pass**다. 이는 선택한 문서의 판정이며 전체 검색 결과의 정확도가 아니다. 검색 관련성 Fail 1건·본문 미확보 판단 불가 1건과 최종 후보 누락 2건이 남았다. **출처 선별은 개선됐지만 Research 전체 개선은 미완료**다. 아래 1~5절은 실험 1, 마지막 실험 2절은 이번 변경의 근거·코드 수정·검증 결과다.

## 2 프롬프트 실험 1 문제에서 수정으로

### 실패를 종합해 어떤 가설을 세웠나

초기 쿼리 Middle 6/6개, Senior 5/6개가 사이트 제한을 사용했다. 공식 기술 문서를 우선하라는 기존 규칙만으로는 운영사 편중과 목록·중복 문서 수집이 억제되지 않았다. 한 운영사에 묶인 검색을 후보의 구체적 동작·문제를 검증하는 검색으로 넓히면 3-1·4-1·5-1이 개선될 수 있다고 봤다. 원래 실험의 주 지표는 4-1, 보조 지표는 5-1이었으며 이번 기록에서 3-1의 실제 결과도 빠짐없이 추가한다.

### 실제 수정 문장과 수정 이유

변경 위치: [초기 조사 프롬프트](../../../src/archgen/research/templates/initial_system.md.j2)의 `출처`. 기존 규칙은 유지하고 **한 항목만 추가**했다. 세 문장을 각각 다음 실패와 연결했다.

| 수정 전의 부족한 점 | 추가 문장 원문 | 이렇게 바꾼 이유와 남는 한계 |
| --- | --- | --- |
| 공식 출처 우선 지시만으로는 한 운영사 사이트 편중을 막지 못함 | 주제 쿼리 외의 후보 쿼리를 모두 같은 서비스 운영사의 사이트로 제한하지 않는다. | 검색 범위를 넓혀 관련 기술 문서를 찾으려는 시도. 검색 결과의 관련성 검사·재검색 규칙 자체를 추가한 것은 아님. |
| 공식 블로그라도 개별 본문 대신 목록이 후보로 선택됨 | 후보의 구체적 동작·문제를 검증할 개별 기술 문서를 찾고, 적합한 기술의 공식 문서·다른 운영사의 기술 글도 검색한다. | 후보의 시스템 동작을 설명하는 문서를 찾도록 구체화. 출처 확대만으로 무관 문서가 자동 제거되지는 않음. |
| 목록·메뉴·홍보 문서 선택이 4-1·5-1에서 반복 Fail | 일반 블로그 목록·메뉴·채용·제품 소개 페이지를 찾는 쿼리는 피한다. | 실패 자료 유형을 명시해 수집 낭비를 줄이려는 시도. URL 중복 제거·Fetch 본문 검증 로직을 추가하지는 않음. |

### 프롬프트에서 실제 바뀐 부분

`출처` 규칙에 아래 한 항목을 추가했다. 기존 문장의 삭제·교체는 없었다.

```diff
+- 주제 쿼리 외의 후보 쿼리를 모두 같은 서비스 운영사의 사이트로 제한하지 않는다. 후보의 구체적 동작·문제를 검증할 개별 기술 문서를 찾고, 적합한 기술의 공식 문서·다른 운영사의 기술 글도 검색한다. 일반 블로그 목록·메뉴·채용·제품 소개 페이지를 찾는 쿼리는 피한다.
```

각 문장의 수정 이유는 바로 위 표에 기록했다.

### 무엇을 고정하고 어떻게 재측정했나

같은 Uber brief·카탈로그·코드·도구 제한으로 Middle·Senior를 수정 전후 각 2회 새로 조사했다. 생성은 Sol medium, 평가는 같은 Research 기준의 Sol high다. 수정 전 4개 생성물과 프롬프트 해시를 확보한 뒤 변경을 적용했다. Keep·Selection·Rubric 프롬프트는 바꾸지 않았다. 새 웹 검색·Fetch이므로 검색 결과와 수집 성공 변동은 남는다.

## 4 채택 판단과 해결하지 못한 문제

**한 항목을 추가한 프롬프트를 잠정 채택한다.** 4-1 평균은 +20.72%p, 5-1은 +17.64%p 개선됐고 6-1·6-2는 유지됐다. 다만 초기 기대와 달리 3-1 Fail 3건, 4-1 Fail 120건, 5-1 Fail 6건이 남았으며 근거 없는 자료·목록·중복 수집과 최종 후보 누락을 해결 완료로 표시하지 않는다.

## 실험 2 순위순 자동 Fetch를 관련성 기반 선택 수집으로 변경

### 왜 initial_system 대신 tools_system을 수정했나

실험 1 뒤에도 4-1 Fail이 120건 남았다. 사용자 지적대로 `tools_system`은 검색 결과 검토 전에 순위순 Fetch를 요구했다. 코드를 확인하니 프롬프트만 바꿔서는 선택 수집을 실행할 수 없었고, 검색 요약도 전달되지 않았다. 이번에는 초기 검색 프롬프트를 그대로 두고 **도구 프롬프트와 그 지시를 막던 코드**를 함께 수정했다. 프롬프트 한 줄만의 효과로 해석하지 않는다.

### 기존에는 왜 그렇게 많은 문서를 수집했나

기존에는 적합한 문서를 고르는 단계 없이 검색 순위대로 계속 Fetch하도록 프롬프트와 코드가 함께 강제했다.

1. `fetch(query_id)`를 호출하면 코드가 미확인 상위 **3개를 자동 수집**했다. Agent가 URL을 선택해 전달할 인자가 없었다.
2. Keep한 문서가 쿼리별 필요 수에 못 미치면 다음 3개를 계속 가져오도록 지시했다.
3. **남은 URL을 전부 수집해야 재검색할 수 있었다.** 코드도 미확인 URL이 있으면 requery를 거부했다.
4. 재검색 결과에서도 같은 순위순 수집을 반복했다.

따라서 **3개는 전체 수집 상한이 아니라 한 번 호출할 때의 배치 크기**였다. 홍보·목록·중복 결과도 미수집 상태로 건너뛰고 재검색할 수 없었다. 기존 Middle 1회차에서는 검색 결과 109개 중 77개를 Fetch했고, 4-1은 그 77개에 대해 Pass 33건·Fail 44건이었다.

변경 후에는 제목·URL·요약을 보고 선택한 URL만 Fetch한다. 적합한 문서가 적으면 배치 수를 채우지 않고, 부적합한 결과는 남겨둔 채 재검색할 수 있다.

Middle 1회차의 실제 전후 비교는 다음과 같다.

- 기존 Middle 1회: 검색 결과 **109개 → 77개 선택 → 33 Pass·44 Fail**
- 수정 후 Middle 1회: 검색 결과 **72개 → 11개 선택 → 11 Pass·0 Fail**

여기서 Pass·Fail의 분모는 전체 검색 결과가 아니라 실제 Fetch 선택 문서 수다. 선택하지 않은 검색 결과를 Pass로 센 것이 아니며, 핵심 근거와 최종 후보 누락은 별도로 확인한다.

### 확인한 문제와 수정 이유

| 발견한 문제 | 실제 수정 전 동작 | 수정 내용 | 왜 함께 수정해야 했나 |
| --- | --- | --- | --- |
| 프롬프트가 순위순 수집을 강제 | 적합하지 않아도 순위대로 배치 수를 채우고, 남은 URL을 소진해야 재검색 | 제목·URL·요약의 사전 검토, 관련성 우선, 적합한 수만 선택, 지역·별칭·추적 URL의 의미상 중복 확인 | 4-1은 Keep 후 결과가 아니라 Fetch 대상으로 선택한 것 자체를 평가함 |

지역별 URL 등의 의미상 중복 판정은 모델의 제목·URL·요약 검토에 맡겼다. 임의의 지역 경로 삭제나 범용 URL 정규화 규칙은 추가하지 않았다. 실제 개선 여부는 새 실행의 4-1 판정에서 확인한다.

### 판단과 남은 문제

**관련성 기반 선택 Fetch는 적용을 유지하되 Research 전체 품질 개선 완료 판정은 보류한다.** 4회 모두 4-1이 100%였고 6-1·6-2도 Pass를 유지했다. 하지만 4-1은 선택 문서만 평가하므로 수집량 감소 자체를 근거 확보 개선으로 해석하지 않는다. 웹 검색 변동과 도구 API·요약 입력·프롬프트 변경이 함께 작용한 관측 결과다.

| 남은 문제 | 당시 판정 기준과 실제 결과 | 후속 검토 |
| --- | --- | --- |
| Middle 2회 검색 결과 관련성 Fail | 3-1: 기술 설계를 검증할 문서 후보가 없고 일반 페이지 결과에 그침. 해당 검색에서 Uber 기술 블로그 목록 변형 1건만 반환됨 | 검색·재검색 쿼리와 결과 부족 시 다음 행동 |
| Middle 2회 본문 미확보 판단 불가 | 5-1: Kafka documentation에서 `Redirecting` 안내만 수집됨. 정상 본문으로 보존하지 않아 Fail 대신 판단 불가로 기록 | 리디렉션 안내와 실제 본문 수집 처리 |
| 최종 후보 누락 1건 → 2건 | Middle 2회 latency, Senior 2회 throughput은 각각 보존 문서 1개로 기존 2개 기준 미달. 본문 근거 확보를 보는 6-1 Pass와 별도로 최종 후보 제외가 실제 발생 | 적합한 근거의 추가 확보·재검색과 후보 제외 기준 검토. 이번 실험에서는 기존 문서 수 기준을 낮추지 않음 |

개별 Fail·판단 불가의 대상·원문 기준·사유는 각 실행 상세 표에 모두 보존했다. 후보 제외는 실제 로그와 최종 후보 목록에 근거한 별도 관찰이며 평가기가 Fail한 것으로 바꿔 적지 않았다. [후보 제외 로그](../../../.archgen/m7-followup/tools-fetch-tuning-20261019/run-2.log).
