# 연차 오류 주입 검증 데이터

원본 데이터셋 ID: `seniority_eval_test_v5`

## 목적

사용자가 승인한 `seniority_eval_clean_v2/01_clean`을 기준으로, **3-5의 Level별 연차 적합성**과 **4-1의 Middle/Senior 실질적 차이**를 검사한다. 정상 한 쌍을 새로 작성하거나 임의로 고치지 않았다.

## v4 대비 변경

E08 3건(`03 Senior C4 L3`, `06 Senior C3 L3`, `07 Senior C2 L3`)을 새로 작성했다. Senior 2점과 같은 요구를 표현만 달리하던 방식에서 벗어나, 구체적인 위험·병목·복구 상황과 한 가지 개선책은 제시하지만 **대안 간 비용 비교와 선택 근거는 빠진** Senior 3점 경계 오류를 만든다. E05는 여전히 분석 대상 자체가 추상적인 오류로 구분한다. E06을 포함한 나머지 21개 오류 문장과 정상본, NFR·배점·범위·기대 Pass/Fail은 그대로 유지한다.

## 구성

| 구분 | 수량 |
|---|---:|
| 승인 정상 한 쌍 | 1쌍 |
| 같은 정상본의 순서·ID 변형 | 1쌍 |
| 서로 다른 Criterion에 오류 4개씩 넣은 사본 | 6쌍 |
| 전체 | 8쌍 / MD 16개 |
| 직접 주입 오류 | 8유형 × 3개 = 24개 |

한 오류 유형의 세 사례는 서로 다른 Criterion에 넣었다. E04와 E07은 동일한 깊이 부족을 어휘 포장형과 직접 복사형으로 나눈 테스트 변형이다. 정상 순서 변형과 오류 변형 모두 같은 공연 예매 주제에서 파생됐으므로 독립적인 다주제 검증은 아니다.

## 평가에 넣을 파일

`cases.json`에서 한 케이스의 `middle`과 `senior` 경로를 읽고, **그 두 MD의 내용 + 현재 사용하는 평가 기준·연차 기준**만 기존 Evaluator에 전달한다. 모든 케이스에 동일한 평가기 설정을 사용한다.

`review/`의 정답·변경 기록·검토표, 이 README, 검증 리포트는 LLM 입력에 넣지 않는다. 케이스 폴더와 파일 본문에는 정상/오류 표식을 넣지 않았다.

전체 Agent나 Research를 재실행하지 않는다. 저장된 두 루브릭을 평가하는 테스트다. 한 쌍을 한 번에 평가하는 구현이면 1회 순회는 8번의 평가 작업이다. 기존 코드가 연차·항목별로 호출을 나누거나 재시도한다면 실제 API 호출 수는 더 많아진다.

## 보존한 기준

Middle 2점 ≈ Senior 1점, Middle 3점 ≈ Senior 2점의 정상본 관계를 기준으로 한다. 같은 기술을 사용한다는 사실만으로 Fail하지 않는다. Senior 2점은 처리 조건과 동작 원리를, 3점은 한계·복잡한 상황과 상충 관계 및 선택 근거를 실제로 요구하는지 본다.

사용자가 승인한 원본 두 파일은 `cases/01/`에 바이트 단위로 보존했다. `cases/04/`는 정상본의 Senior C3·C4와 관련 NFR의 순서·번호만 교환했다. 둘 다 20점이며 서술은 바꾸지 않았다. 정상 원본에 있던 다른 특징은 임의로 교정하지 않았다.

## 결과 확인

1. `3-5`는 각 Level의 원문·판정·근거와 Criterion 최종 판정을 확인한다.
2. `4-1`은 대응 Criterion과 추가 필수 역량의 차이를 확인한다. 한 쌍의 Fail만으로 모든 오류 탐지로 집계하지 않는다.
3. `review/expected_labels.md`와 JSON에 대조해 주입 오류 24개의 탐지 여부와 정상 항목의 오탐을 각각 기록한다.

Middle 2점에 과도한 요구를 넣은 E02는 「2점에 더해」로 연결된 Middle 3점에도 영향을 준다. 직접 주입과 연쇄 영향을 라벨에 구분했으며 같은 오류를 두 번 세지 않는다. E01·E06의 주 검증은 3-5이고, 반드시 각각 별도의 4-1 실패를 만들 필요는 없다.

평가 기준이나 원문이 예측과 다르게 해석되는 경우 원문을 확인한다. 예상 목록에 없다는 이유만으로 추가 지적을 오탐으로 확정하지 않는다. 이 묶음은 3-5·4-1 검증용이며 나머지 Rubric 품질 기준의 전체 정답은 아니다.

## 결과를 전달할 때

각 케이스의 ID, 사용한 평가·연차 기준 버전, 모델 설정, Evaluator의 원래 JSON을 함께 보관한다. 3-5의 Level별 판정·근거와 4-1의 대응 항목별 근거가 포함되어야 오류별 검출을 확인하기 쉽다. 기존 출력 형식을 새로 구현할 필요는 없다.

`review/results_template.json`은 선택적인 정리 양식이다. 실제 점수와 근거를 아직 채우지 않았으며 `null`은 여기서 미실행 빈칸이지 Evaluator의 판단 불가 판정이 아니다.

## 검증 상태

오류 라벨은 제작 시 정한 기대 판정이다. 정상 원본은 사용자가 승인했지만 오류 정답을 외부 평가기로 검증했다고 주장하지 않는다. **실제 LLM 호출은 수행하지 않았다.** 파일 보존·배점·문장 길이·변경 위치·오류 개수·라벨 정합성만 코드로 검증했다. 결과는 `validation_report.json`에 있다.

기존에 제공한 `seniority_eval_dataset.zip` 및 `seniority_eval_dataset_corrected.zip`과 섞지 말고 이번 폴더만 사용한다.
