# 공연 좌석 티켓 예매

**설계 범위**
공연별 잔여 좌석 조회, 좌석의 임시 점유·만료, 주문 접수와 외부 결제 결과에 따른 예매 확정·해제를 설계한다. 환불·재판매·추천은 제외한다.

**평가 초점**
좌석 중복 예매 방지, 점유 만료·지연 결제의 정합성, 예매 오픈 시 요청 폭증 대응, 접수한 주문의 장애 후 복구와 중복 확정 방지

**대상 연차** Middle\
**배점** 100

## NFR-1. Consistency

**요구 수준**
`consistency` — 동시 요청에서도 같은 좌석의 유효한 점유·확정이 충돌하지 않아야 한다. 만료된 점유나 늦은 결제 결과가 새로운 소유자의 상태를 덮어쓰지 않아야 한다.

### C1. 좌석 점유와 예매 확정의 정합성 · 35

**평가 항목**
좌석 점유·만료·결제 결과에 따른 소유권 확인과 상태 전이를 평가한다. 장애 후 주문 복구는 제외한다.

| Level | 기준 |
|---|---|
| 0 | 같은 좌석을 여러 사용자가 동시에 점유해 중복 예매될 수 있다는 문제를 고려하지 않는다. |
| 1 | 좌석 저장소가 경쟁 중인 요청 하나에만 점유를 허용하며, 점유한 사용자를 확인한 다음 결제 결과에 맞춰 확정 또는 해제로 상태를 바꾸는 과정을 설명한다. |
| 2 | 좌석 상태를 관리하는 저장소에서 한 요청만 점유에 성공하게 하고, 점유자 확인 후 결제 결과에 따라 확정하거나 해제하는 기본 흐름을 설명한다. |
| 3 | 2점에 더해, 늦은 결제 응답이 만료된 점유를 확정할 수 있다는 한계를 설명한다. 확정 전에 점유 유효성을 다시 확인하는 기본 개선 방안을 제시한다. |

---

## NFR-2. Fault Tolerance

**요구 수준**
`fault_tolerance` — 접수 완료 주문은 처리 중 장애 이후에도 복구할 수 있어야 하며, 재시도나 결제 결과의 중복 전달이 예매 확정을 중복 반영해서는 안 된다.

### C2. 접수 주문 보존과 장애 후 재개 · 25

**평가 항목**
주문 접수 성공 이후 보존·재처리와 외부 결제 결과 조정을 평가한다. 정상 경합에서의 좌석 소유권 규칙은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 접수한 주문이 처리 중 장애로 유실될 수 있다는 문제를 고려하지 않는다. |
| 1 | 장애 후 재시도하겠다고 제안하지만, 어떤 주문을 어디에 저장하고 누가 다시 처리하는지 설명하지 못한다. |
| 2 | 주문을 지속 저장한 뒤 접수 성공을 반환하고, 작업자가 미완료 주문을 찾아 처리한 후 완료 상태를 기록하는 기본 흐름을 설명한다. |
| 3 | 2점에 더해, 완료 기록 전에 장애가 나면 주문이 다시 처리될 수 있다는 한계를 설명한다. 기존 처리 결과를 확인해 중복 확정을 피하는 개선 방안을 제시한다. |

---

## NFR-3. High Throughput

**요구 수준**
`throughput` — 예매 오픈 시 요청 유입이 처리 가능량을 넘어도 점유·주문 경로의 적체가 무제한 늘지 않도록 제어하고 이미 진입한 작업을 보호해야 한다.

### C3. 초과 유입과 적체 제어 · 20

**평가 항목**
처리 용량을 넘는 유입의 대기·제한 정책과 내부 작업 보호를 평가한다. 처리 자원 증설 자체는 제외한다.

| Level | 기준 |
|---|---|
| 0 | 예매 오픈 때 처리 능력을 넘는 요청으로 내부 작업이 무제한 쌓일 수 있다는 문제를 고려하지 않는다. |
| 1 | 요청을 대기시키거나 제한하겠다고 하지만, 제한 지점과 초과 요청의 처리 흐름을 설명하지 못한다. |
| 2 | 유입 제한·대기·거절의 기본 흐름과 함께, 공유 카운터 갱신 병목과 진입 서버 장애 시 상한 회수의 정합성을 분석한다. 중앙 집계와 서버별 허용량 분할을 비교해 전체 상한 보장·남는 용량 활용·조정 비용의 상충과 선택 근거를 설명한다. |
| 3 | 2점에 더해, 대기 중인 사용자의 재시도가 동시에 몰려 다시 과부하가 생기는 한계를 설명한다. 재시도 시점을 분산하는 기본 개선 방안을 제시한다. |

## NFR-4. Scalability

**요구 수준**
`scalability` — 조회 요청과 서로 다른 좌석의 점유 작업이 증가하면 처리 자원을 늘려 수용 범위를 넓힐 수 있어야 한다. 인기 공연의 집중 부하와 동일 좌석 충돌은 구분해야 한다.

### C4. 인기 공연의 조회·점유 처리 확장 · 20

**평가 항목**
조회·점유 경로의 자원 분산과 인기 공연에 집중된 부하의 확장 단위를 평가한다. 요청 제한 정책은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 인기 공연에 조회·점유가 몰릴 때 서버 확장이 필요하다는 문제를 고려하지 않는다. |
| 1 | 서버를 늘리겠다고 제안하지만, 조회·점유 요청을 여러 서버에 어떻게 분산하는지 설명하지 못한다. |
| 2 | 조회 서버와 점유 서버의 역할을 구분하고, 공연별 요청을 여러 처리 서버로 나눠 부하를 분담하는 기본 흐름을 설명한다. |
| 3 | 2점에 더해, 인기 공연 하나에 요청이 집중되면 공연별 분산만으로 병목이 남는 한계를 설명한다. 좌석군처럼 더 작은 단위로 점유 요청을 분산하는 개선 방안을 제시한다. |
