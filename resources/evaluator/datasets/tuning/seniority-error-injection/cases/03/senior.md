# 공연 좌석 티켓 예매

**설계 범위**
공연별 잔여 좌석 조회, 좌석의 임시 점유·만료, 주문 접수와 외부 결제 결과에 따른 예매 확정·해제를 설계한다. 환불·재판매·추천은 제외한다.

**평가 초점**
좌석 중복 예매 방지, 점유 만료·지연 결제의 정합성, 예매 오픈 시 요청 폭증 대응, 접수한 주문의 장애 후 복구와 중복 확정 방지

## NFR-1. Consistency

**요구 수준**
`consistency` — 동시 요청에서도 같은 좌석의 유효한 점유·확정이 충돌하지 않아야 한다. 만료된 점유나 늦은 결제 결과가 새로운 소유자의 상태를 덮어쓰지 않아야 한다.

### C1. 좌석 점유와 예매 확정의 정합성 · 35

**평가 항목**
좌석 점유·만료·결제 결과에 따른 소유권 확인과 상태 전이를 평가한다. 장애 후 주문 복구는 제외한다.

| Level | 기준 |
|---|---|
| 0 | 같은 좌석을 여러 사용자가 동시에 점유해 중복 예매될 수 있다는 문제를 고려하지 않는다. |
| 1 | 좌석 저장소에서 한 요청만 점유하게 하고, 점유자를 확인해 결제 결과에 따라 확정하거나 해제하는 흐름을 제시한다. 다만 확인 이후 만료·재점유가 끼어들 때 변경을 막는 구체적인 조건은 설명하지 못한다. |
| 2 | 가용 좌석에 점유 ID·만료 시각을 원자적으로 기록한다. 확정은 점유 ID 일치·대기 상태·미만료 조건에서, 해제는 같은 ID·대기 상태에서 만료나 결제 실패 조건으로 원자 갱신해 오래된 응답이 새 점유나 확정을 바꾸지 못하게 한다. |
| 3 | 2점에 더해, 좌석 상태 전이의 복잡한 예외와 심층적인 한계를 분석하고 고도화된 아키텍처의 Trade-off를 종합적으로 검토하여 최적의 설계를 정당화한다. |

## NFR-2. Fault Tolerance

**요구 수준**
`fault_tolerance` — 접수 완료 주문은 처리 중 장애 이후에도 복구할 수 있어야 하며, 재시도나 결제 결과의 중복 전달이 예매 확정을 중복 반영해서는 안 된다.

### C2. 접수 주문 보존과 장애 후 재개 · 25

**평가 항목**
주문 접수 성공 이후 보존·재처리와 외부 결제 결과 조정을 평가한다. 정상 경합에서의 좌석 소유권 규칙은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 접수한 주문이 처리 중 장애로 유실될 수 있다는 문제를 고려하지 않는다. |
| 1 | 주문과 진행 상태를 저장한 뒤 접수 성공을 반환하고, 작업자가 미완료 주문을 찾아 처리한 뒤 완료로 기록하는 흐름을 제시한다. 다만 같은 주문이 다시 처리될 때 중복 확정을 막는 구체적인 조건은 설명하지 못한다. |
| 2 | 주문 접수·재개 흐름에서 주문 ID별 확정 기록에 유일성 제약을 두고, 확정 결과와 완료 상태를 같은 트랜잭션으로 저장한다. 재처리·중복 결제 통지는 기존 기록이 있으면 결과를 재사용하고, 없으면 새로 반영하되 경합한 작업 중 한 건만 커밋되게 한다. |
| 3 | 2점에 더해, 결제 성공 후 내부 기록 전에 장애가 난 상황에서 기존 결제 식별자로 외부 결과를 대조해 복구하는 흐름을 분석한다. 외부 결제까지 로컬 트랜잭션으로 묶을 수 없는 한계를 짚고, 대사 주기에 따른 복구 지연·조회 부하와 선택 근거를 설명한다. |

## NFR-3. High Throughput

**요구 수준**
`throughput` — 예매 오픈 시 요청 유입이 처리 가능량을 넘어도 점유·주문 경로의 적체가 무제한 늘지 않도록 제어하고 이미 진입한 작업을 보호해야 한다.

### C3. 초과 유입과 적체 제어 · 20

**평가 항목**
처리 용량을 넘는 유입의 대기·제한 정책과 내부 작업 보호를 평가한다. 처리 자원 증설 자체는 제외한다.

| Level | 기준 |
|---|---|
| 0 | 예매 오픈 때 처리 능력을 넘는 요청으로 내부 작업이 무제한 쌓일 수 있다는 문제를 고려하지 않는다. |
| 1 | 앞단에서 처리 가능한 수만 점유·주문 서비스로 보내고 초과 요청은 대기시키거나 거절하는 흐름을 제시한다. 다만 여러 진입 서버가 허용량을 나눠 쓰거나 대기자가 동시에 재시도할 때의 제어 방식은 설명하지 못한다. |
| 2 | 진입 요청을 앞단에서 제한해 처리 가능한 수만 점유·주문 서비스로 보내고, 나머지는 대기시키거나 거절하는 기본 흐름을 설명한다. |
| 3 | 2점에 더해, 모든 진입 서버가 공유 카운터를 갱신해 진입 판단 자체가 병목이 되는 상황을 분석한다. 전체 상한을 서버별로 나눠 관리하는 대안과 비교해 조정 비용·남는 용량의 활용·서버 장애 시 용량 회수의 상충을 설명하고 선택을 정당화한다. |

## NFR-4. Scalability

**요구 수준**
`scalability` — 조회 요청과 서로 다른 좌석의 점유 작업이 증가하면 처리 자원을 늘려 수용 범위를 넓힐 수 있어야 한다. 인기 공연의 집중 부하와 동일 좌석 충돌은 구분해야 한다.

### C4. 인기 공연의 조회·점유 처리 확장 · 20

**평가 항목**
조회·점유 경로의 자원 분산과 인기 공연에 집중된 부하의 확장 단위를 평가한다. 요청 제한 정책은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 인기 공연에 조회·점유가 몰릴 때 서버 확장이 필요하다는 문제를 고려하지 않는다. |
| 1 | 조회 서버와 점유 서버의 역할을 나누고, 공연별 요청을 여러 처리 서버로 분산해 부하를 나누는 흐름을 제시한다. 다만 인기 공연 하나에 요청이 집중될 때 요청과 점유 데이터를 함께 나눌 방법은 설명하지 못한다. |
| 2 | 조회는 읽기 복제본이나 캐시로 보내고, 점유 상태는 공연 ID·좌석군 기준으로 여러 저장소에 분할한다. 라우터는 분할표로 담당 저장소를 찾아 같은 좌석의 변경을 같은 곳으로 보낸다. 서버만 늘려도 남는 단일 쓰기 저장소 병목을 줄이는 흐름을 설명한다. |
| 3 | 2점에 더해, 좌석군을 다른 저장소로 재배치할 때 이전 경로로 점유 쓰기가 들어와 두 저장소가 동시에 같은 좌석을 변경할 수 있음을 지적한다. 이를 막기 위해 해당 좌석군의 쓰기를 잠시 중단하고 데이터를 복사한 뒤 라우팅을 전환하는 절차를 제시한다. |
