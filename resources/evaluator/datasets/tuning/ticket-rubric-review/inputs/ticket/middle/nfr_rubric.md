# 공연 좌석 티켓 예매

**설계 범위**
공연별 좌석 잔여 현황 조회, 좌석 임시 점유와 만료, 주문 생성과 외부 결제 결과에 따른 예매 확정 또는 해제까지 설계한다. 결제 대행사 내부 구현·환불·재판매·공연 추천은 제외한다.

**평가 초점**
동일 좌석의 중복 예매 방지, 점유 만료·지연 결제 응답·재시도의 상태 일관성, 예매 오픈 시 조회·점유 요청 폭증 대응, 접수된 주문의 장애 후 복구와 중복 확정 방지

**대상 연차** Middle\
**배점** 100

## NFR-1. Consistency

**요구 수준**
`consistency` — 동시 요청에서도 같은 좌석에 서로 충돌하는 점유나 예매를 성공시키지 않는다. 지연 결제 응답과 오래된 만료 작업은 현재 소유권과 확정 상태를 덮어쓰지 않는다. 조회에 보인 잔여 좌석은 점유 성공을 보장하지 않으며, 실제 점유·확정 시 유효성을 판정한다.
동일 공연의 동일 좌석에는 유효한 점유 소유자와 확정 예매가 충돌하지 않아야 하며, 점유·만료·결제 결과·재시도의 경합에서도 허용된 상태 전이만 반영되어야 한다.

### C1. 좌석 점유와 예매 상태 전이의 정합성 · 30

**평가 항목**
동일 공연·좌석의 점유부터 확정·해제까지 소유권과 유효성을 판정하는 흐름을 평가하며, 만료·지연 결제·재시도의 경합은 포함하되 장애 후 주문 복구 절차는 구분한다.

| Level | 기준 |
|---|---|
| 0 | 동일 좌석의 점유나 확정 요청이 충돌할 수 있다는 문제를 고려하지 않고, 요청마다 독립적으로 성공 처리한다. |
| 1 | 중복 예매 위험을 인식하고 잠금이나 상태 검사 등의 해결책을 제시하지만, 점유 소유권·만료·결제 결과에 따라 성공과 해제를 판정하는 흐름을 충분히 설명하지 못한다. |
| 2 | 조회 결과와 실제 점유 판정을 구분하고, 권위 있는 판정 지점에서 충돌하는 변경을 함께 성공시키지 않는 흐름을 설명한다. 소유권·유효성을 확인하며 만료·지연 결제·재시도에 적용할 일관된 정책과 구성요소의 역할을 제시한다. |
| 3 | 2점에 더해, 좌석 재할당 뒤 도착한 결제 결과나 오래된 만료 작업이 현재 상태를 덮어쓸 수 있는 한계를 사례로 설명하고, 현재 점유와 확정 상태를 구분하여 잘못된 변경을 막는 개선을 제시한다. |

## NFR-2. Fault Tolerance

**요구 수준**
`fault_tolerance` — 주문 접수를 성공으로 응답한 뒤 처리 프로세스가 중단되어도 주문과 처리 진행 상태를 복구할 수 있다. 동일 요청이나 결제 이벤트를 다시 처리해도 예매 확정 효과는 중복되지 않는다. 결제 결과를 받지 못했거나 점유 만료와 충돌한 주문은 확인 가능한 미결 상태로 남겨 외부 상태와 대사하며, 이미 재할당된 좌석을 중복 확정하지 않는다.
접수한 주문은 처리 중 장애와 외부 결제 결과의 유실·중복 전달 이후에도 복구 가능해야 하며, 복구와 재시도가 중복 주문 효과나 중복 예매 확정을 만들지 않아야 한다.

### C2. 접수 주문의 복구와 중복 효과 방지 · 25

**평가 항목**
접수 성공 이후의 주문·처리 상태 보존, 장애 후 재처리와 외부 결제 결과 대사를 평가하며, 복구 과정의 중복 효과 방지를 다루되 좌석 자체의 충돌 판정은 구분한다.

| Level | 기준 |
|---|---|
| 0 | 접수 후 프로세스 중단이나 결제 결과 유실·중복 전달을 고려하지 않고, 정상 응답을 받는 경로만 설계한다. |
| 1 | 주문 유실과 중복 처리 위험을 인식하고 저장이나 재시도를 제안하지만, 접수 성공 전 보존할 정보와 복구 대상 식별, 중복 반영 방지의 기본 흐름을 충분히 설명하지 못한다. |
| 2 | 접수 성공 전에 주문과 진행 상태를 보존하고 장애 후 이어 처리하는 흐름을 설명한다. 요청·이벤트 재처리의 중복 효과를 막고, 결제 결과가 불명확한 주문을 미결로 추적하여 외부 상태와 대사하는 구성요소의 역할을 제시한다. |
| 3 | 2점에 더해, 단순 재전달만으로는 누락된 결제 결과를 찾지 못하거나 재처리 도중 다시 중단될 수 있음을 설명한다. 미결 주문을 다시 찾아 확인하고 중복 반영 없이 재개하는 개선으로 복구의 빈틈을 보완한다. |

## NFR-3. High Throughput

**요구 수준**
`throughput` — 검증된 처리 능력에 맞추어 유입을 제어하고, 초과 요청은 대기 또는 명시적인 제한 응답으로 처리한다. 요청 폭증이 내부 작업의 무제한 적체나 전체 처리 실패로 이어지지 않도록 하며, 이미 진입한 요청의 처리를 지속할 수 있어야 한다. 구체적인 처리량과 동시 사용자 한도는 부하 검증으로 정한다.
예매 오픈 시 요청 유입이 처리 능력을 넘더라도 실제 처리 경로에 전달되는 부하를 제어하여, 접수한 조회·점유·주문 처리가 과부하로 함께 붕괴하지 않아야 한다.

### C3. 처리 능력에 맞춘 유입 제어 · 25

**평가 항목**
예매 오픈 시 조회·점유·주문 경로로 들어오는 부하의 수용 판단과 초과 요청 처리를 평가하며, 이미 접수한 작업의 진행 보호를 포함하되 처리 자원 확장 자체는 구분한다.

| Level | 기준 |
|---|---|
| 0 | 요청 유입이 처리 능력을 초과하는 상황을 고려하지 않고, 모든 요청을 제한 없이 내부 처리 경로에 전달한다. |
| 1 | 과부하 위험을 인식하고 대기나 제한을 제안하지만, 어느 지점에서 수용을 판단하고 초과 요청과 이미 접수된 작업을 어떻게 처리하는지 충분히 설명하지 못한다. |
| 2 | 부하 검증으로 확인한 처리 능력에 맞춰 유입을 제어하는 흐름과 구성요소의 역할을 설명한다. 초과 요청은 대기 또는 명시적 제한으로 처리하고, 내부 적체를 제한하여 이미 접수한 작업의 진행을 보호한다. |
| 3 | 2점에 더해, 처리 능력 변화나 제한받은 요청의 반복 유입으로 고정된 수용 기준이 맞지 않을 수 있음을 설명한다. 적체와 처리 상태를 관찰하여 유입량이나 재시도 안내를 조정하는 개선을 제시한다. |

## NFR-4. Scalability

**요구 수준**
`scalability` — 공연 수와 요청량 증가에 따라 처리 자원을 추가해 수용 범위를 넓힐 수 있어야 한다. 인기 공연에 부하가 집중되는 경우에도 추가 자원이 효과를 내는 분산 단위와 남는 병목을 설명하고 검증할 수 있어야 한다. 동일 좌석의 충돌 판정을 병렬화한다는 이유로 정합성을 약화하지 않는다.
조회·점유 부하가 증가할 때 자원과 처리 범위를 확장할 수 있어야 하며, 특정 인기 공연에 집중된 부하가 하나의 고정된 처리 단위에만 묶이지 않도록 해야 한다.

### C4. 부하 증가와 인기 공연 집중에 대한 확장 · 20

**평가 항목**
조회·점유 경로에서 자원 추가가 수용 범위 증가로 이어지는 처리 분산 구조를 평가하며, 인기 공연 내부의 확장 단위와 남는 병목을 포함하되 초과 유입 제한 정책은 구분한다.

| Level | 기준 |
|---|---|
| 0 | 공연 수나 요청량 증가에 따른 처리 자원 확장과 특정 인기 공연으로의 부하 집중을 고려하지 않는다. |
| 1 | 서버 증설이나 공연별 분산을 제안하지만, 조회·점유 요청이 추가 자원으로 어떻게 나뉘는지 또는 인기 공연이 단일 처리 단위에 묶이는 문제를 충분히 설명하지 못한다. |
| 2 | 조회·점유의 주요 구성요소와 요청 분산 흐름을 설명하고, 인기 공연 내부에도 추가 자원이 효과를 내는 처리 단위를 제시한다. 동일 좌석의 충돌 판정을 유지하면서 남는 병목과 부하 검증 방법을 설명한다. |
| 3 | 2점에 더해, 제시한 분산 단위에서도 부하 편중이나 공통 처리 지점 때문에 확장 효과가 제한되는 사례를 설명한다. 해당 병목에 맞춰 분산 단위를 조정하거나 집중 작업을 줄이는 개선을 제시한다. |
