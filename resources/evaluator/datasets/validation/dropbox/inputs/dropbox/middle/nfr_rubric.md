# Dropbox 파일 동기화

**설계 범위**
클라이언트의 파일 업로드·수정·삭제, 파일 내용과 버전 메타데이터 저장, 여러 기기의 변경 감지와 다운로드 동기화, 연결 중단 후 재개까지 설계한다. 문서 공동 편집·공개 링크 공유·파일 내용 검색은 제외한다.

**평가 초점**
중단된 대용량 파일 전송의 재개, 파일 내용과 버전 메타데이터의 일관성, 오프라인 및 동시 수정 충돌 처리, 많은 파일과 기기의 변경 탐지·동기화 부하 관리

**대상 연차** Middle\

## NFR-1. Consistency

**요구 수준**
`consistency` — 완료된 것으로 관찰되는 버전은 그 버전에 대응하는 전체 내용을 조회할 수 있어야 하며, 누락되거나 검증에 실패한 내용을 정상 버전으로 공개하지 않는다. 전송 중 데이터의 선행 다운로드를 허용하더라도 완료된 버전과 구분한다.
완료된 파일 버전으로 공개되는 메타데이터는 실제로 확보된 해당 버전의 파일 내용과 일치해야 한다.

### C1. 파일 내용과 완료 버전의 일치 · 30

**평가 항목**
파일 업로드·수정에서 단일 버전의 내용 확보와 검증, 메타데이터 공개, 다른 기기의 조회 흐름을 평가하며 여러 변경 사이의 충돌 조정은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 완료 버전의 메타데이터가 실제로 확보된 파일 내용과 일치해야 한다는 문제를 고려하지 않는다. |
| 1 | 내용을 저장한 뒤 버전을 공개하는 기본 방안을 제시하지만, 내용 저장소와 메타데이터 관리의 역할이나 누락·검증 실패 시 처리 흐름을 충분히 설명하지 못한다. |
| 2 | 내용 저장과 버전 메타데이터 관리의 역할을 구분하고, 해당 버전의 전체 내용 확보와 검증 후 완료 상태를 공개하여 다른 기기가 대응하는 내용을 조회하는 기본 흐름을 설명한다. |
| 3 | 2점에 더해, 내용 저장 후 메타데이터 갱신이 실패하는 등 단계 사이 중단의 한계를 설명하고, 미완료 상태를 정상 버전과 구분하면서 재확인 후 공개하는 개선 방안을 제시한다. |

## NFR-2. Fault Tolerance

**요구 수준**
`fault_tolerance` — 재개 가능한 전송 상태가 유효한 동안 연결이 복구되면 확인된 완료 부분을 다시 보내지 않고 미완료 또는 실패한 부분부터 진행한다. 재개 결과가 원래 전송하려던 파일 버전과 일치하는지 확인한 뒤 완료로 처리한다.
파일 전송 중 연결이 끊겨도 이미 완료된 전송 부분을 재사용하여 안전하게 전송을 재개할 수 있어야 한다.

### C2. 연결 중단 후 부분 전송 재사용 · 25

**평가 항목**
업로드·다운로드의 재개 상태가 유효한 동안 연결 복구 후 완료 부분을 재사용하고 원래 파일 버전으로 전송을 마치는 흐름을 평가한다.

| Level | 기준 |
|---|---|
| 0 | 연결 중단 후 완료된 전송 부분을 식별하고 재사용해야 한다는 문제를 고려하지 않는다. |
| 1 | 전송을 나누고 실패한 부분을 재시도하는 방안을 제시하지만, 완료 부분을 기록·확인하는 역할이나 재연결 후 이어 보내는 흐름을 충분히 설명하지 못한다. |
| 2 | 클라이언트와 서버가 전송 대상 버전과 진행 상태를 식별하는 역할을 설명하고, 유효한 상태에서 확인된 완료 부분은 재전송하지 않으며 나머지를 전송한 뒤 원래 버전과 일치하는지 확인하는 흐름을 제시한다. |
| 3 | 2점에 더해, 완료 응답 유실로 양측의 진행 기록이 달라질 수 있음을 설명하고, 실제 완료 부분을 다시 확인하여 불필요한 재전송이나 잘못된 완료 판정을 줄이는 개선 방안을 제시한다. |

## NFR-3. Consistency

**요구 수준**
`consistency` — 연결이 복구되고 추가 변경이 멈춘 조건에서 각 기기는 조정된 파일 상태로 수렴한다. 같은 대상을 오프라인 또는 동시에 수정·삭제했을 때의 처리 규칙을 정의하고, 그 결과가 데이터 모델의 불변조건을 깨뜨리지 않도록 한다. 특정 충돌 사본 형식이나 모든 변경의 자동 병합은 강제하지 않는다.
오프라인 기기의 변경과 동시 변경은 재연결 후 정의된 충돌 처리 규칙에 따라 조정되어 유효한 파일 상태로 수렴해야 한다.

### C3. 오프라인·동시 변경의 충돌 조정 · 25

**평가 항목**
여러 기기의 수정·삭제 충돌 판정과 결과 전파를 평가하며 연결 복구 후 필요한 전송이 가능하고 추가 변경이 멈춘 조건에서의 상태 수렴을 다룬다.

| Level | 기준 |
|---|---|
| 0 | 오프라인 또는 동시 수정·삭제가 같은 파일에 충돌하는 상황과 이를 조정할 필요를 고려하지 않는다. |
| 1 | 충돌 시 선택이나 보존 같은 기본 정책을 제시하지만, 변경의 기준 상태를 비교하는 방법이나 조정 결과를 다른 기기에 반영하는 흐름을 충분히 설명하지 못한다. |
| 2 | 변경의 기준 버전 등으로 충돌을 판정하고 수정·삭제에 적용할 규칙을 설명하며, 기기와 서버의 역할 및 조정 결과의 전파 흐름을 통해 조건 충족 시 유효한 동일 상태로 수렴함을 설명한다. |
| 3 | 2점에 더해, 늦게 도착한 과거 변경이 조정된 상태를 다시 뒤집을 수 있는 한계를 설명하고, 변경의 선후 관계 확인 등으로 기존 규칙에 맞게 재조정하는 개선 방안을 제시한다. |

## NFR-4. High Throughput

**요구 수준**
`throughput` — 변경 탐지에서 반복적인 전체 스캔 의존을 줄이고, 부하 제한 시 재시도가 요청량을 증폭시키지 않도록 한다. 동기화 작업과 임시 데이터의 증가를 제어하면서 대기 중인 변경 처리를 계속 진행할 수 있어야 한다. 구체적인 처리량과 허용 적체 시간은 부하 조건 확정 후 정한다.
많은 파일과 기기에서 변경 탐지·동기화 요청이 발생해도 불필요한 반복 조회와 재시도 증폭으로 유효한 변경 처리 능력이 소진되지 않아야 한다.

### C4. 변경 탐지와 동기화 부하 제어 · 20

**평가 항목**
많은 파일·기기의 변경 탐지와 동기화에서 반복 조회, 재시도, 작업 및 임시 데이터 증가를 제어하는 흐름을 평가하며 수치 처리량이나 지연 보장은 요구하지 않는다.

| Level | 기준 |
|---|---|
| 0 | 반복적인 전체 조회와 제한 없는 동기화·재시도가 유효한 변경 처리를 방해할 수 있다는 문제를 고려하지 않는다. |
| 1 | 증분 탐지나 실행량 제한 같은 기본 방안을 제시하지만, 변경 탐지부터 대기 작업 처리까지의 역할이나 부하 제한 시 재시도 흐름을 충분히 설명하지 못한다. |
| 2 | 전체 스캔 의존을 줄이는 변경 탐지 흐름과 주요 구성요소의 역할을 설명하고, 실행량·재시도·임시 데이터 증가를 제어하면서 대기 변경을 계속 처리하는 기본 설계를 제시한다. |
| 3 | 2점에 더해, 여러 기기가 동시에 재연결하면 실행량을 제한해도 대기 요청이 몰릴 수 있음을 설명하고, 요청 시점 분산이나 유입 속도 조절 등으로 적체를 완화하는 개선 방안을 제시한다. |
