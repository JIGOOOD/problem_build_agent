# Dropbox 파일 동기화

**설계 범위**
클라이언트의 파일 업로드·수정·삭제, 파일 내용과 버전 메타데이터 저장, 여러 기기의 변경 감지와 다운로드 동기화, 연결 중단 후 재개까지 설계한다. 문서 공동 편집·공개 링크 공유·파일 내용 검색은 제외한다.

**평가 초점**
중단된 대용량 파일 전송의 재개, 파일 내용과 버전 메타데이터의 일관성, 오프라인 및 동시 수정 충돌 처리, 많은 파일과 기기의 변경 탐지·동기화 부하 관리

**대상 연차** Senior\
**배점** 100

## NFR-1. Consistency

**요구 수준**
`consistency` — 공개된 버전의 메타데이터는 완성된 해당 파일 내용을 가리켜야 한다. 오프라인·동시 수정과 수정·삭제 충돌은 명시한 정책에 따라 처리하고, 변경이 계속 발생하지 않으며 연결이 복구된 조건에서는 기기들이 조정된 상태로 수렴해야 한다. 충돌 정책은 미확정이며, 동시 변경이 충돌 처리 없이 조용히 소실되는 결과를 방지해야 한다.
파일 내용과 공개된 버전 메타데이터가 일치하고, 오프라인 변경과 동시 변경을 조정할 때 유효한 파일 상태를 유지해야 한다.

### C1. 버전 공개와 충돌 조정의 정합성 · 30

**평가 항목**
파일 업로드·수정·삭제에서 내용과 버전 메타데이터의 공개 경계, 오프라인·동시 변경의 충돌 판정과 조정 후 수렴을 평가하며 전송 진행 상태의 복구 절차는 제외한다.

| Level | 기준 |
|---|---|
| 0 | 완성된 파일 내용과 공개 버전의 대응 관계를 고려하지 않고, 오프라인·동시 변경의 충돌을 판정하거나 조정하는 설계도 제시하지 않는다. |
| 1 | 내용 저장 후 버전을 공개하고 충돌을 처리하는 기본 설계를 제시하지만, 저장 실패나 동시 갱신에서 공개 경계를 지키는 방법 또는 수정·삭제 충돌의 처리 흐름을 구체화하지 못한다. |
| 2 | 완성된 내용만 가리키도록 버전 공개를 제어하는 메커니즘과 실패 시 처리를 설명한다. 기준 버전 등으로 충돌을 판정하고 수정·삭제를 포함한 조정 정책을 명시하며, 조용한 변경 소실을 막고 연결 복구 후 변경이 멎으면 기기들이 수렴하는 흐름을 제시한다. |
| 3 | 2점에 더해, 오래된 기기의 변경이 조정 중 다시 도착하는 등 복잡한 순서에서 정책의 한계를 분석하고 개선을 설명한다. 선택한 공개·조정 경계가 주는 정합성과 처리 비용의 절충을 비교하며, 여러 샤드의 원자적 변경을 택한 경우에만 그 조정 비용까지 다룬다. |

## NFR-2. Fault Tolerance

**요구 수준**
`fault_tolerance` — 재개 가능한 상태가 유효한 동안에는 서버 또는 수신 측이 확인한 진행 지점부터 미완료 부분을 이어서 전송할 수 있어야 한다. 응답 유실 시 전송 완료를 추정하지 않고 상태를 확인하며, 미완성 파일을 완료된 버전으로 노출하지 않아야 한다. 재개 상태가 만료되거나 무효화된 경우에는 이를 감지하고 안전한 재동기화 경로로 복구해야 한다.
파일 전송이 연결 중단으로 실패하거나 완료 여부가 불명확해져도, 확인 가능한 진행 상태를 바탕으로 안전하게 동기화를 재개해야 한다.

### C2. 중단된 전송의 진행 확인과 재개 · 25

**평가 항목**
업로드와 다운로드의 연결 중단·응답 유실에서 진행 상태 확인, 재개 대상 식별, 완료 판정과 무효 상태 복구를 평가하며 충돌 정책과 버전 공개의 원자성은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 전송 중단이나 완료 응답 유실을 고려하지 않으며, 확인된 진행 상태를 이용해 미완료 부분을 재개하는 설계를 제시하지 않는다. |
| 1 | 진행 위치를 기록하고 재시도하는 기본 설계를 제시하지만, 송신량과 실제 수신량의 차이, 완료 여부가 불명확한 경우 또는 재개 상태가 무효인 경우의 처리 절차를 설명하지 못한다. |
| 2 | 업로드·다운로드에서 재개 대상과 수신 측이 확인한 진행 상태를 연결하고 미완료 부분을 이어가는 메커니즘을 설명한다. 응답 유실 시 상태를 확인해 완료를 판정하고, 미완성을 완료로 취급하지 않으며, 만료·무효 상태를 감지해 안전하게 재동기화한다. |
| 3 | 2점에 더해, 반복 중단이나 진행 기록과 실제 수신 상태의 차이로 생기는 재전송·확인 비용을 분석하고 개선안을 제시한다. 복구 단위와 확인 빈도가 재전송 부담, 추가 요청, 메모리 사용에 미치는 영향을 비교해 선택 근거를 설명한다. |

## NFR-3. Scalability

**요구 수준**
`scalability` — 초기 열거 또는 복구를 위한 재열거 이후에는 변경량에 대응하는 증분 동기화가 가능해야 한다. 파일·기기·감시 범위 증가에 따라 연결과 변경 처리 부하를 집계하거나 분산할 수 있어야 하며, 변경 추적 상태가 만료되면 누락 없이 기준 상태를 다시 확보할 수 있어야 한다. 구체적인 규모와 확장 비율은 미확정이다.
파일과 기기 수가 증가해도 변경 감지와 동기화 작업을 전체 목록 반복 조회나 감시 연결의 무제한 증가에 의존하지 않고 확장할 수 있어야 한다.

### C3. 변경 추적과 감시 부하의 확장 · 25

**평가 항목**
파일·기기·감시 범위 증가에 따른 증분 변경 탐지, 감시 연결과 변경 처리의 집계·분산, 추적 상태 만료 후 기준 상태 복구를 평가하며 주어진 자원의 작업 처리 효율은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 파일과 기기가 늘어날 때 전체 목록 반복 조회나 감시 연결 증가가 만드는 부하를 고려하지 않고, 변경 추적을 확장하는 설계를 제시하지 않는다. |
| 1 | 증분 조회와 알림 등으로 변경을 탐지하는 기본 설계를 제시하지만, 감시 범위별 연결 증가나 변경 처리 집중을 제어하는 방법 또는 추적 상태 만료 후 복구 흐름을 구체화하지 못한다. |
| 2 | 초기 열거 후 변경량에 대응하는 증분 조회 메커니즘을 설명하고, 감시 연결과 변경 처리 부하를 집계하거나 분산한다. 알림과 실제 변경 조회의 역할을 구분하며, 추적 상태 만료 시 누락 없이 기준 상태와 후속 변경 추적을 다시 확보하는 흐름을 제시한다. |
| 3 | 2점에 더해, 특정 감시 범위로의 부하 편중이나 재열거 집중 등 선택한 설계의 확장 한계를 분석하고 개선안을 제시한다. 감시 범위 집계나 분산 단위 조정이 연결 수, 불필요한 조회, 상태 관리 복잡도에 주는 절충과 선택 근거를 설명한다. |

## NFR-4. High Throughput

**요구 수준**
`throughput` — 명시한 자원과 부하 조건에서 대량 변경과 동시 전송을 계속 처리하고, 과도한 병렬 작업으로 처리량이 악화되거나 자원 사용이 무제한 증가하지 않도록 해야 한다. 일시적으로 작업이 몰린 뒤에는 잔여 자원에 맞춰 적체를 해소할 수 있어야 한다. 보장할 처리량과 적체 해소 시간은 부하 가정이 확정된 뒤 정한다.
다수 파일의 변경과 동시 전송을 처리할 때 저장장치·네트워크·연산 자원의 한계 안에서 유효한 동기화 처리량을 유지해야 한다.

### C4. 자원 한계 내 동기화 처리량 · 20

**평가 항목**
설계에서 명시한 자원·부하 조건 아래 변경 처리와 동시 전송의 병렬성, 대기 작업량 및 적체 해소를 평가하며 파일·기기 증가에 따른 감시 구조의 확장은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 대량 변경과 동시 전송이 저장장치·네트워크·연산 자원을 경쟁하는 문제를 고려하지 않고, 병렬 작업이나 대기 작업량을 제어하는 설계를 제시하지 않는다. |
| 1 | 병렬 처리나 작업 대기열을 사용하는 기본 설계를 제시하지만, 병렬성 증가가 실제 병목 자원과 메모리에 미치는 영향 또는 일시적 작업 집중 후 적체를 해소하는 방법을 구체화하지 못한다. |
| 2 | 자원과 부하 가정을 명시하고 읽기·해시·전송·쓰기 중 관련 병목을 분석한다. 병렬성과 진행 중·대기 작업량을 제한하거나 유입을 제어하는 메커니즘으로 자원 사용의 무제한 증가를 막고, 작업 집중 후 잔여 자원에 맞춰 적체를 해소하는 흐름을 설명한다. |
| 3 | 2점에 더해, 고정된 병렬성이나 전송 단위가 자원 경합 변화에 대응하지 못하는 한계를 분석하고 관측 결과에 따른 조정 방안을 설명한다. 전송 단위·진행 확인 빈도·병렬성 선택에 따른 처리량, 메모리, 재전송 비용의 절충과 선택 근거를 제시한다. |
