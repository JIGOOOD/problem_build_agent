# Slack 채널 메시징

**설계 범위**
워크스페이스의 채널에서 텍스트 메시지 전송·저장·실시간 전달, 메시지 이력 조회와 연결 중단 후 누락 메시지 동기화까지 설계한다. 검색·파일 첨부·음성 및 영상 통화는 제외한다.

**평가 초점**
접수된 메시지의 유실 방지, 재시도·재접속 시 중복과 채널 내 순서 처리, 온라인 수신자의 메시지 전달 지연, 대규모 채널의 메시지 전달 부하 분산

**대상 연차** Senior\
**배점** 100

## NFR-1. Fault Tolerance

**요구 수준**
`fault_tolerance` — 설계에서 명시한 장애 범위 안에서 성공 응답한 메시지가 이력과 누락분 복구에서 사라지지 않아야 한다. 일시적 연결 복원이 실패해도 저장된 메시지를 기준으로 동기화를 완료할 수 있어야 한다. 허용 장애 범위와 보존 기간은 별도 확정한다.
성공으로 접수한 메시지는 장애나 연결 중단 뒤에도 이력에서 조회하고 누락분을 동기화할 수 있어야 한다.

### C1. 성공 접수 메시지의 영속화와 누락 복구 · 30

**평가 항목**
설계에서 명시한 장애·보존·동기화 가능 범위 안에서 성공 응답의 영속화 경계와 이력 조회 및 누락분 복구 경로를 평가하며, 중복 반영과 순서 결정은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 성공으로 접수한 메시지가 장애 뒤에도 남아 있어야 한다는 문제와 연결 중단 뒤 누락분을 복구하는 경로를 고려하지 않는다. |
| 1 | 저장 후 성공 응답하고 재접속 시 이력을 조회하는 기본 설계를 제시하지만, 영속화 완료의 판단 기준이나 저장과 전달 사이 장애가 발생했을 때의 복구 처리를 구체적으로 설명하지 못한다. |
| 2 | 보장할 장애 범위를 명시하고 성공 응답을 영속화 확인과 연결하는 메커니즘을 설명한다. 저장과 전달 사이 장애에도 이력 조회가 가능하고, 일시적 연결 복원이 실패하면 저장된 메시지로 누락분을 복구하는 흐름을 제시한다. |
| 3 | 2점에 더해, 선택한 영속화·복구 경로의 한계와 개선을 설명한다. 영속화 확인 대기와 접수 응답 시간의 절충을 분석하고, 전달도 확인 뒤로 제한한다면 수신 지연에 미치는 영향까지 근거로 선택을 설명한다. |

## NFR-2. Consistency

**요구 수준**
`consistency` — 동일한 논리 메시지를 재시도하거나 재접속 후 다시 받아도 저장·표시에 중복 반영하지 않아야 한다. 동기화가 완료된 수신자들은 동일 채널의 메시지를 합의된 순서 규칙에 따라 관찰해야 한다. 동시 전송의 순서 결정 기준은 명시하되 채널 간 전역 순서는 요구하지 않는다.
동일 메시지의 재시도와 재전달은 중복된 논리 메시지를 만들지 않아야 하며, 채널의 실시간 수신과 이력·누락분 동기화 결과는 정의된 채널 내 순서로 합쳐져야 한다.

### C2. 논리 메시지 중복 방지와 채널 내 병합 순서 · 30

**평가 항목**
재시도·재전달의 저장 및 표시 중복 방지와 실시간·이력·누락분의 채널 내 순서 병합을 평가하며, 채널 간 전역 순서나 모든 읽기의 즉시 최신성은 요구하지 않는다.

| Level | 기준 |
|---|---|
| 0 | 재시도와 재전달이 논리 메시지를 중복 생성하는 문제나 실시간 수신과 이력·누락분의 순서가 어긋나는 문제를 고려하지 않는다. |
| 1 | 메시지 식별과 채널 정렬을 이용하는 기본 설계를 제시하지만, 동시 재시도의 중복 저장 방지나 이력 조회 중 도착한 실시간 메시지의 병합 처리를 구체적으로 설명하지 못한다. |
| 2 | 동일 논리 메시지의 식별 범위와 중복 저장·표시 방지 메커니즘을 설명한다. 동시 전송의 채널 내 순서 결정 기준을 정하고, 재전달·역순 도착·이력과 실시간 수신의 겹침을 처리하여 동기화 후 같은 순서로 병합하는 흐름을 제시한다. |
| 3 | 2점에 더해, 선택한 중복 판정이나 순서 병합 방식이 재시도·재접속의 복잡한 경계에서 갖는 한계를 분석하고 개선한다. 식별·순서 상태의 유지 부담이나 순서 확정 대기와 처리 효율 사이의 절충을 설명하고 선택 근거를 제시한다. |

## NFR-3. Low Latency

**요구 수준**
`latency` — 메시지 전송 요청부터 온라인 수신자의 관찰까지를 전달 지연으로 평가하고, 발신자 접수 응답 시간과 구분한다. 정상 부하와 대규모 채널 부하에서 전달 경로의 대기 및 꼬리 지연이 커지는 원인을 관리해야 한다. 수치 목표, 백분위와 측정 부하 조건은 미확정이다.
정상 연결된 온라인 수신자가 채널 메시지를 관찰하기까지의 지연을 낮게 유지해야 한다.

### C3. 온라인 수신자의 전달 경로와 지연 관리 · 20

**평가 항목**
정상 연결된 온라인 수신자에 대해 전송 요청부터 메시지 관찰까지의 단계별 대기와 꼬리 지연 관리를 평가하며, 자원 확장의 분산 단위와 상태 이동 설계는 제외한다.

| Level | 기준 |
|---|---|
| 0 | 온라인 수신자가 메시지를 관찰하기까지 거치는 전달 경로나 그 과정에서 발생하는 대기와 지연을 고려하지 않는다. |
| 1 | 실시간 전달 경로와 지연을 줄이는 기본 방안을 제시하지만, 발신자 접수 응답과 수신자 관찰 시점을 구분하지 못하거나 주요 단계의 대기 원인과 처리 방안을 구체적으로 설명하지 못한다. |
| 2 | 접수 응답과 수신자 관찰을 구분하여 전달 경로의 단계별 처리·대기를 설명한다. 정상 부하와 대규모 채널에서 큐 적체나 전송 대기가 꼬리 지연을 키우는 지점을 짚고, 해당 대기를 줄이거나 격리하는 구체적인 메커니즘을 제시한다. |
| 3 | 2점에 더해, 제시한 지연 개선이 부하 쏠림이나 느린 수신자 상황에서 갖는 한계를 분석하고 보완한다. 선택한 방식의 대기 감소와 자원 사용·처리 효율 사이 절충을 설명하고, 요청부터 관찰까지의 경로를 기준으로 개선 근거를 제시한다. |

## NFR-4. Scalability

**요구 수준**
`scalability` — 대규모 채널의 전달 부하가 단일 처리 주체의 용량에만 묶이지 않고 추가 자원을 활용할 수 있어야 한다. 확장 과정에서 구독 상태의 복제·이동이 새로운 병목이 되는지 설명해야 한다. 특정 제품의 연결 수나 팬아웃 절감률은 요구 규모로 적용하지 않는다.
채널 수와 연결 수의 증가뿐 아니라 단일 대규모 채널의 수신자 증가에도 전달 처리 용량을 확장할 수 있어야 한다.

### C4. 단일 대규모 채널의 전달 용량 확장 · 20

**평가 항목**
채널·연결 증가와 단일 대규모 채널의 수신자 증가에 대응하는 전달 작업 분산 및 구독 상태 확장 비용을 평가하며, 전달 지연 자체의 개선 효과는 별도로 채점하지 않는다.

| Level | 기준 |
|---|---|
| 0 | 채널·연결 증가나 단일 대규모 채널의 수신자 증가에 따라 전달 작업이 특정 처리 주체에 집중되는 문제를 고려하지 않는다. |
| 1 | 채널이나 연결을 여러 처리 주체에 나누는 기본 설계를 제시하지만, 단일 대규모 채널이 추가 자원을 활용하는 방식이나 확장 시 구독 상태를 배치·이동하는 흐름을 구체적으로 설명하지 못한다. |
| 2 | 채널·연결의 분산 단위와 전달 경로를 설명하고, 단일 대규모 채널의 전달 작업도 여러 자원에 나누는 메커니즘을 제시한다. 자원을 추가할 때 구독 상태의 복제·이동과 작업 재배치가 만드는 병목을 짚고 대응 방안을 설명한다. |
| 3 | 2점에 더해, 분산 이후에도 남는 집중 지점이나 구독 상태 복제·이동 비용이 확장을 제한하는 상황을 분석하고 개선한다. 분산 단위와 상태 배치 선택에 따른 작업 균형·조정 부담·이동 비용의 절충을 비교하고 선택 근거를 설명한다. |
