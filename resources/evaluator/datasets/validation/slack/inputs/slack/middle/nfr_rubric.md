# Slack 채널 메시징

**설계 범위**
워크스페이스의 채널에서 텍스트 메시지 전송·저장·실시간 전달, 메시지 이력 조회와 연결 중단 후 누락 메시지 동기화까지 설계한다. 검색·파일 첨부·음성 및 영상 통화는 제외한다.

**평가 초점**
접수된 메시지의 유실 방지, 재시도·재접속 시 중복과 채널 내 순서 처리, 온라인 수신자의 메시지 전달 지연, 대규모 채널의 메시지 전달 부하 분산

**대상 연차** Middle\
**배점** 100

## NFR-1. Fault Tolerance

**요구 수준**
`fault_tolerance` — 접수 성공으로 확정한 메시지가 합의한 장애 후에도 이력에 남아야 한다. 실시간 전달 누락은 재접속 후 이력과 대조하여 복구할 수 있어야 하며, 처리 결과가 불확실한 요청은 성공으로 단정하지 않고 안전하게 재확인하거나 재시도할 수 있어야 한다.
성공적으로 접수한 메시지는 합의한 장애 범위에서 유실되지 않으며, 연결 중단으로 실시간 전달을 놓친 메시지는 저장된 이력으로 복구할 수 있어야 한다.

### C1. 접수 메시지 보존과 누락 복구 · 30

**평가 항목**
접수 성공 시점과 합의한 장애 범위에서의 메시지 보존, 합의한 이력 보존 범위 안에서의 재접속 누락 복구 흐름을 평가하며, 중복 반영과 순서 판단은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 접수 성공한 메시지의 장애 후 보존이나 연결 중단으로 놓친 메시지의 복구를 설계에서 고려하지 않는다. |
| 1 | 저장과 재시도, 이력 조회로 유실을 막으려 하지만, 성공 응답과 기록 완료의 관계 또는 재접속 후 누락분을 찾는 흐름을 충분히 설명하지 못한다. |
| 2 | 접수 성공 시점과 보장할 장애 범위를 명시하고, 보존을 담당하는 구성요소와 기록·응답 흐름을 설명한다. 결과가 불확실한 요청의 재확인이나 재시도, 보존 범위 내 이력 기반 누락 복구 흐름도 설명한다. |
| 3 | 2점 설계에 더해, 기록 완료 확인이 전달 대기를 늘리는 등 보존 방식의 대표적 한계를 짚고, 합의한 보존 수준을 낮추지 않으면서 대기를 줄이거나 복구 흐름을 개선하는 방안을 설명한다. |

## NFR-2. Consistency

**요구 수준**
`consistency` — 동시 전송된 메시지에 채널별로 일관된 확정 순서를 부여하고, 실시간 수신과 이력 조회가 같은 메시지 집합과 순서로 수렴해야 한다. 응답 유실에 따른 재시도와 재접속 시 조회 구간 중첩이 사용자에게 중복 메시지로 남지 않아야 한다.
같은 채널의 확정된 메시지는 사용자와 조회 경로 사이에서 일관된 순서로 관찰되어야 하며, 재시도와 재접속 동기화가 같은 메시지를 별개의 메시지로 중복 반영하지 않아야 한다.

### C2. 채널 순서와 중복 없는 반영 · 30

**평가 항목**
같은 채널의 동시 전송에 대한 확정 순서와 재시도·재접속 시 이력 및 실시간 메시지의 중복 없는 병합을 평가하며, 저장 내구성과 전달 용량은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 같은 채널에서 사용자나 조회 경로별로 순서가 달라지는 문제와 재시도·재접속으로 메시지가 중복 반영되는 문제를 고려하지 않는다. |
| 1 | 채널별 정렬과 중복 제거를 제안하지만, 동시 전송의 순서 결정 기준이나 재시도 요청의 식별, 이력과 실시간 메시지를 합치는 흐름을 충분히 설명하지 못한다. |
| 2 | 채널별 확정 순서를 정하는 역할과 기준을 제시하고, 요청·메시지 식별을 이용해 재시도와 조회 구간 중첩을 중복 반영하지 않는 흐름을 설명한다. 이력과 실시간 수신이 같은 메시지 집합과 순서로 수렴하도록 설계한다. |
| 3 | 2점 설계에 더해, 이력 조회 중 실시간 메시지가 도착해 단순 병합의 경계가 흔들리는 등 대표적 한계를 설명하고, 조회 경계 조정이나 식별값 기반 재정렬 등으로 같은 순서에 수렴시키는 개선을 제시한다. |

## NFR-3. Low Latency

**요구 수준**
`latency` — 송신 요청부터 정상 연결된 온라인 수신자의 수신까지 측정 구간을 명시하고, 저장·큐잉·팬아웃 과정의 대기로 실시간 대화가 장시간 정체되지 않도록 해야 한다. 백분위와 부하별 수치 기준은 별도 합의가 필요하다.
온라인 수신자는 채널 메시지를 대화에 적합한 낮은 지연으로 전달받아야 한다.

### C3. 온라인 전달 경로와 지연 관리 · 20

**평가 항목**
명시한 온라인 전달 대상과 구독 정책에 따라 송신 요청부터 정상 연결 수신자의 수신까지의 지연 경로와 대기 완화 설계를 평가하며, 자원 증가에 따른 용량 확장은 제외한다.

| Level | 기준 |
|---|---|
| 0 | 정상 연결된 온라인 수신자에게 메시지가 도달하기까지의 지연이나 전달 경로의 대기를 고려하지 않는다. |
| 1 | 실시간 연결이나 비동기 전달로 지연을 줄이려 하지만, 전달 대상과 측정 구간 또는 저장·큐잉·팬아웃을 거치는 기본 흐름을 충분히 설명하지 못한다. |
| 2 | 온라인 전달 대상과 구독 정책, 송신 요청부터 수신까지의 측정 구간을 명시한다. 저장·큐잉·팬아웃 구성요소의 역할과 전달 흐름을 설명하고, 불필요한 대기로 대화가 장시간 정체되지 않도록 설계한다. |
| 3 | 2점 설계에 더해, 느린 수신자나 큐 적체가 다른 수신자의 전달까지 늦추는 등 대표적 한계를 설명한다. 대기 구간을 구분해 확인하고, 필요한 전달과 메시지 보존을 유지하면서 대기를 분리하거나 줄이는 개선을 제시한다. |

## NFR-4. Scalability

**요구 수준**
`scalability` — 온라인 수신자와 메시지 유입이 증가하면 전달 작업을 추가 자원에 분산할 수 있어야 한다. 단일 대규모 채널이 하나의 전달 처리 주체에 묶이지 않아야 하며, 확장 과정에서도 메시지 복구와 채널 순서 요구를 유지해야 한다.
채널 수와 온라인 수신자 수가 늘어날 때 전달 용량을 확장할 수 있어야 하며, 단일 대규모 채널의 팬아웃도 여러 처리 주체로 분산할 수 있어야 한다.

### C4. 대규모 채널의 전달 작업 분산 · 20

**평가 항목**
채널 수와 온라인 수신자 증가에 따른 전달 용량 확장 및 단일 대규모 채널 내부의 작업 분산을 평가하며, 순서·복구는 유지할 제약으로만 확인하고 그 처리 로직은 재평가하지 않는다.

| Level | 기준 |
|---|---|
| 0 | 채널 수나 온라인 수신자가 늘어날 때 전달 작업이 한 처리 주체에 집중되는 문제를 고려하지 않는다. |
| 1 | 서버 추가나 채널별 분할을 제안하지만, 단일 대규모 채널의 전달 작업을 여러 처리 주체에 나누는 기준과 흐름을 충분히 설명하지 못한다. |
| 2 | 채널 간 부하와 단일 대규모 채널의 수신자별 전달 작업을 추가 자원에 나누는 구조를 제시한다. 분할 기준, 구성요소의 역할과 전달 흐름을 설명하고, 분산 후에도 기존 순서·복구 경로가 유지됨을 설명한다. |
| 3 | 2점 설계에 더해, 분산해도 중계 지점이나 과도한 구독 상태 복제가 새 병목이 되는 등 대표적 한계를 설명한다. 순서·복구 요구를 유지하면서 분산 단위나 상태 배치를 조정하는 개선과 그에 따른 부담을 설명한다. |
