# Uber 차량 매칭

**설계 범위**
운전자 위치 갱신과 승객의 차량 호출 접수부터 주변 운전자 검색, 호출 전달, 배정 확정 또는 매칭 실패까지 설계한다. 운행 진행, 요금 계산, 결제는 제외한다.

**평가 초점**
운전자 중복 배정 방지, 주변 운전자 검색 지연, 장애 시 호출 요청 보존과 재처리, 대규모 위치 업데이트 처리

**대상 연차** Senior\
**배점** 100

## NFR-1. Strong Consistency

**요구 수준**
`consistency` — 시스템은 한 운전자에게 여러 운행이 동시에 배정되지 않도록, 차량 매칭 과정에서 강한 일관성을 보장해야 한다.

### C1. 운전자 중복 배정 방지 · 35

**평가 항목**
동일한 운전자에게 여러 차량 호출 요청이 동시에 전송되는 일을 어떻게 방지할 것인가?

| Level | 기준 |
| --- | --- |
| 0 | 동일한 운전자에게 여러 차량 호출이 동시에 전송될 수 있다는 문제를 고려하지 않는다. |
| 1 | 운전자에게 호출 요청을 보낼 때 여러 인스턴스가 공유하는 lock을 획득하고, 일정 시간 내 수락하지 않으면 타이머로 해제하는 기본 설계를 제시한다. 다만 잠금 획득 조건이나 인스턴스 장애 시 잠금 해제 방법은 구체적으로 설명하지 못한다. |
| 2 | DB 트랜잭션으로 운전자 가용 확인과 요청 대기 전환을 원자적으로 처리한다. 수락·거절에 따라 상태를 변경하고, 타이머 유실은 DB의 만료 시각을 주기적으로 확인해 복구한다. 다만 만료 확인이 늦어지거나 DB 조회 부하가 증가할 수 있다. |
| 3 | 주기적 만료 검사에 따른 해제 지연과 DB 부하를 줄이기 위해 Redis TTL 락 등 자동 만료 방식을 검토한다. 락 만료·늦은 수락에도 DB에서 중복 확정을 방지하고, Redis 장애 의존성과 운영 비용을 비교해 선택을 정당화한다. |

## NFR-2. Low Latency

**요구 수준**
`latency` — 시스템은 지연 시간이 짧은 매칭을 우선시해야 한다. 이를 위해 주변 운전자 후보 검색에서 불필요한 조회 범위와 대기 시간을 줄여야 한다.

### C2. 주변 운전자 검색 최적화 · 30

**평가 항목**
빈번한 운전자 위치 업데이트와 위치 데이터에 대한 효율적인 근접 검색을 어떻게 처리할 것인가?

| Level | 기준 |
| --- | --- |
| 0 | 운전자 위치 업데이트와 위치 데이터에 대한 효율적인 근접 검색 처리 방법을 고민하지 않는다. |
| 1 | 운전자의 위치 업데이트가 도착할 때마다 데이터베이스에 직접 기록하고, 공간 인덱스로 근접 검색을 수행하는 기본 설계를 제시한다. 다만 대량의 업데이트를 처리할 방법이나 근접 검색의 구체적인 동작은 설명하지 못한다. |
| 2 | 짧은 시간의 위치 갱신을 배치 처리해 DB 쓰기를 줄이고, 쿼드트리 등 공간 인덱스로 주변 운전자를 검색한다. 갱신 간격을 조절해 오래된 위치 문제를 완화하지만, 간격을 줄이면 쓰기 부하가 커지는 한계가 남는다. |
| 3 | 2점의 배치 갱신이 가진 위치 최신성과 DB 쓰기 부하의 상충을 줄이기 위해 Redis GEO 등 인메모리 공간 검색을 검토한다. 실시간 위치 갱신과 빠른 검색을 구현하고, 위치 유실 위험·메모리 비용·장애 대응 부담을 비교해 선택 근거를 설명한다. |

## NFR-3. Fault Tolerance

**요구 수준**
`fault_tolerance` — 접수 완료된 차량 호출 요청은 피크 부하나 매칭 서비스 장애에도 유실되지 않고, 복구 후 안전하게 재처리될 수 있어야 한다.

### C3. 호출 요청 보존 및 장애 후 재처리 · 20

**평가 항목**
호출 요청의 안전한 보존과 장애 후 재처리 메커니즘을 평가하며, 중복 실행 위험과 처리 보장 수준에 따른 Trade-off를 다룬다.

| Level | 기준 |
| --- | --- |
| 0 | 호출 요청이 매칭 서비스 장애로 유실될 수 있다는 문제를 고려하지 않는다. |
| 1 | 큐를 통한 요청 보관과 처리 흐름은 제시하지만, 접수 성공 시점의 보존 여부나 장애 후 복구·중복 처리 방안을 구체적으로 설명하지 못한다. |
| 2 | 내구성 있는 메시지 큐에 요청을 저장한 뒤 접수 성공을 반환하고, 처리 완료 후에만 확인 응답이나 오프셋을 커밋한다. 장애 시 미완료 요청을 재처리하며 동일 호출의 중복 효과를 방지하는 흐름을 설명한다. |
| 3 | 2점에 더해, 처리 결과 저장과 완료 확인 사이에 장애가 발생하여 요청이 재처리되는 상황을 분석한다. 멱등 처리의 보장 범위와 재시도 지연·상태 관리 비용의 Trade-off를 설명하고 기술 선택을 정당화한다. |

## NFR-4. High Throughput

**요구 수준**
`throughput` — 시스템은 특히 피크 시간이나 특별 이벤트에서 높은 처리량을 감당해야 한다. 이를 위해 빈번한 운전자 위치 업데이트를 수신·처리하고 검색용 위치 상태에 반영하면서 적체가 계속 누적되지 않도록 한다.

### C4. 대규모 위치 업데이트 처리 · 15

**평가 항목**
위치 정확도를 유지하면서 빈번한 운전자 위치 업데이트로 발생하는 시스템 과부하를 어떻게 관리할 것인가?

| Level | 기준 |
| --- | --- |
| 0 | 위치 정확도를 유지하면서 빈번한 운전자 위치 업데이트로 발생하는 시스템 과부하를 어떻게 관리할지 고민하지 않는다. |
| 1 | 운전자의 위치 업데이트를 처리하는 서버를 수평 확장하여 처리량을 늘린다. 하지만 위치 업데이트 발생량 자체는 줄이지 못하므로 운전자 수가 증가할수록 데이터베이스 등의 하위 시스템에 병목이 발생하거나 운영 비용이 증가할 수 있다. |
| 2 | 운전자의 마지막 전송 위치와 현재 위치의 거리를 비교해 일정 거리 이상 변경되었을 때만 업데이트하여 불필요한 전송을 줄인다. 하지만 고정된 거리 기준만 사용하므로 운전자의 이동 방향이나 호출 요청 상황 등에 따라 요구되는 위치 정확도를 유연하게 반영하기 어렵다. |
| 3 | 운전자의 속도, 이동 방향, 상태 등에 따라 위치 업데이트 주기를 동적으로 조정한다. 정지하거나 느리게 이동할 때는 빈도를 줄이고, 빠르게 이동하거나 방향을 자주 바꿀 때는 높인다. 고정 거리 기준의 정확도 한계를 분석하고, 위치 정확도·전송량·알고리즘 복잡성·검증 비용의 Trade-off와 선택 근거를 설명한다. |
