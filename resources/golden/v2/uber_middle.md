# Uber 차량 매칭

**설계 범위**
운전자 위치 갱신과 승객의 차량 호출 접수부터 주변 운전자 검색, 호출 전달, 배정 확정 또는 매칭 실패까지 설계한다. 운행 진행, 요금 계산, 결제는 제외한다.

**평가 초점**
운전자 중복 배정 방지, 주변 운전자 검색 지연, 장애 시 호출 요청 보존과 재처리, 대규모 위치 업데이트 처리

**대상 연차** Middle\
**배점** 100

## NFR-1. Strong Consistency

**요구 수준**
`consistency` — 시스템은 한 운전자에게 여러 운행이 동시에 배정되지 않도록, 차량 매칭 과정에서 강한 일관성을 보장해야 한다.

### C1. 운전자 중복 배정 방지 · 35

**평가 항목**
동일한 운전자에게 여러 차량 호출 요청이 동시에 전송되는 일을 어떻게 방지할 것인가?

| Level | 기준 |
| --- | --- |
| 0 | 운전자 한 명에게 여러 호출 요청이 겹쳐 전달될 수 있다는 문제를 고려하지 않는다. |
| 1 | 운전자 상태를 확인하거나 잠금을 사용하겠다고 제안하지만, 여러 요청이 동시에 들어올 때 한 요청만 운전자를 확보하는 흐름을 설명하지 못한다. |
| 2 | 공유된 운전자 상태의 가용 여부 확인과 요청 대기 상태 변경을 한 번에 처리하여 한 요청만 운전자를 확보하도록 한다. 수락하면 배정 상태를 유지하고 거절하면 가용 상태로 바꾸는 기본 흐름을 설명한다. |
| 3 | 2점에 더해, 무응답으로 요청 대기 상태가 계속 남는 문제를 설명한다. 일정 시간 내 응답이 없고 해당 요청이 여전히 대기 중인 경우에만 상태를 해제하여, 이미 수락된 호출은 유지하는 기본적인 타임아웃 방안을 제시한다. |

## NFR-2. Low Latency

**요구 수준**
`latency` — 시스템은 지연 시간이 짧은 매칭을 우선시해야 한다. 이를 위해 주변 운전자 후보 검색에서 불필요한 조회 범위와 대기 시간을 줄여야 한다.

### C2. 주변 운전자 검색 최적화 · 30

**평가 항목**
빈번한 운전자 위치 업데이트와 위치 데이터에 대한 효율적인 근접 검색을 어떻게 처리할 것인가?

| Level | 기준 |
| --- | --- |
| 0 | 운전자 위치를 갱신하고 주변 운전자를 검색하는 경로를 고려하지 않는다. |
| 1 | 위치를 저장하거나 공간 인덱스를 사용하겠다고 제안하지만, 각 구성 요소의 역할이나 위치 갱신부터 근접 검색까지의 흐름을 설명하지 못한다. |
| 2 | 운전자가 보낸 위치를 저장소에 반영하고, 승객의 위치를 기준으로 가까운 운전자를 조회하는 흐름을 설명한다. 공간 인덱스로 검색 범위를 줄여 모든 운전자의 위치를 확인하지 않도록 한다. |
| 3 | 2점에 더해, 위치 업데이트마다 저장하면 쓰기 부하가 커지는 한계를 설명한다. 짧은 시간 동안 업데이트를 모아 저장하는 등 쓰기 부담을 줄이는 기본 개선 방안을 제시한다. |

---

## NFR-3. Fault Tolerance

**요구 수준**
`fault_tolerance` — 접수 완료된 차량 호출 요청은 피크 부하나 매칭 서비스 장애에도 유실되지 않고, 복구 후 안전하게 재처리될 수 있어야 한다.

### C3. 호출 요청 보존 및 장애 후 재처리 · 20

**평가 항목**
접수된 호출 요청을 안전하게 보관하고, 매칭 서비스 장애 후에도 미완료 요청을 다시 처리하는 기본 흐름을 평가한다.

| Level | 기준 |
| --- | --- |
| 0 | 호출 요청이 매칭 서비스 장애로 유실될 수 있다는 문제를 고려하지 않는다. |
| 1 | 요청을 큐에 저장하겠다고 제안하지만, 요청을 어디에 보관하고 누가 처리하며 언제 완료되는지 설명하지 못한다. |
| 2 | 호출 요청을 내구성 있는 큐에 보관하고, 매칭 서비스가 가져와 처리한 뒤 완료를 표시하는 기본 흐름을 설명한다. 완료되지 않은 요청은 다시 처리할 수 있음을 설명한다. |
| 3 | 2점에 더해, 매칭 서비스가 처리 도중 중단되거나 완료 기록 전에 종료될 수 있음을 설명한다. 재처리 시 이미 완료된 요청인지 확인하여 중복 처리를 피하는 기본 방안을 제시한다. |

---

## NFR-4. High Throughput

**요구 수준**
`throughput` — 시스템은 특히 피크 시간이나 특별 이벤트에서 높은 처리량을 감당해야 한다. 이를 위해 빈번한 운전자 위치 업데이트를 수신·처리하고 검색용 위치 상태에 반영하면서 적체가 계속 누적되지 않도록 한다.

### C4. 대규모 위치 업데이트 처리 · 15

**평가 항목**
위치 정확도를 유지하면서 빈번한 운전자 위치 업데이트로 발생하는 시스템 과부하를 어떻게 관리할 것인가?

| Level | 기준 |
| --- | --- |
| 0 | 운전자 위치의 전송 빈도와 서버 처리 부하의 관계를 고려하지 않는다. |
| 1 | 위치 업데이트가 많아지면 서버를 늘리겠다고 제안하지만, 늘어난 서버가 어떤 작업을 나누어 처리하는지 설명하지 못한다. |
| 2 | 운전자 앱이 보낸 위치 업데이트를 여러 처리 서버에 나누어 전달하고 저장소에 반영하는 흐름을 설명한다. 서버를 추가하면 위치 업데이트 처리 작업을 분담할 수 있음을 설명한다. |
| 3 | 2점에 더해, 서버를 늘려도 불필요한 위치 전송 자체는 줄지 않는 한계를 설명한다. 위치가 일정 거리 이상 변했을 때만 새 위치를 보내는 등 불필요한 전송을 줄이는 기본 개선 방안을 제시한다. |
