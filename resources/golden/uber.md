## NFR-1. Low Latency

**요구 수준**
`latency` — 시스템은 지연 시간이 짧은 매칭을 우선시해야 한다(매칭되거나 매칭 실패가 결정되기까지 1분 미만).

### C1. 주변 운전자 검색 최적화 · 30

**평가 항목**
빈번한 운전자 위치 업데이트와 위치 데이터에 대한 효율적인 근접 검색을 어떻게 처리할 것인가?


| Level | 기준 |
|---|---|
| 0 | 운전자 위치 업데이트와 위치 데이터에 대한 효율적인 근접 검색 처리 방법을 고민하지 않는다. |
| 1 | 운전자의 위치 업데이트가 도착할 때마다 데이터베이스에 직접 기록하고, 이 원시 데이터를 대상으로 근접 검색을 수행한다. 수백만 명의 운전자로부터 들어오는 대량의 업데이트를 감당하기 어렵고 근접 검색이 비효율적이며 느려지기 때문에 좋지 않은 방법으로 여겨진다. |
| 2 | 짧은 시간 동안 업데이트를 모았다가 배치로 처리해 쓰기 작업 횟수를 줄인다. 근접 검색에는 쿼드트리와 같은 적절한 인덱싱이 적용된 전문 지리 공간 데이터베이스를 사용하여 가까운 운전자를 효율적으로 조회한다. 다만 배치 쓰기 간격 때문에 최신 운전자 위치가 데이터베이스에 즉시 반영되지 않아 최적이 아닌 매칭이 발생할 수 있다. |
| 3 | Redis처럼 지리 공간 데이터 타입과 명령어를 지원하는 인메모리 데이터 저장소를 사용한다. 이를 통해 낮은 지연 시간으로 실시간 운전자 위치 업데이트와 근접 검색을 처리하면서, 데이터 자동 만료 기능으로 저장 비용을 최소화한다. 다만 인메모리 저장소는 장애 시 위치 데이터가 유실될 수 있으므로, Redis 영속성 설정이나 Sentinel을 통한 장애 조치 등을 고려할 수 있다. |

## NFR-2. Strong Consistency

요구 수준
`consistency` — 시스템은 한 운전자에게 여러 운행이 동시에 배정되지 않도록, 차량 매칭 과정에서 강한 일관성을 보장해야 한다.

### C2. 운전자 중복 배정 방지 · 35

평가 항목
동일한 운전자에게 여러 차량 호출 요청이 동시에 전송되는 일을 어떻게 방지할 것인가?

| Level | 기준 |
|---|---|
| 0 | 동일한 운전자에게 여러 차량 호출이 동시에 전송될 수 있다는 문제를 고려하지 않는다. |
| 1 | 운전자에게 여러 차량 호출 요청이 동시에 전송되지 않도록 운전자를 lock한다. 차량 매칭 서비스의 각 인스턴스는 운전자에게 호출 요청을 보낼 때 해당 요청을 lock 상태로 표시한다. 그런 다음 잠금 지속 시간을 추적할 타이머를 시작한다. 운전자가 이 기간 내에 호출을 수락하지 않으면 해당 인스턴스가 수동으로 잠금을 해제하여 운전자가 다시 다른 요청을 받을 수 있게 한다. 다만 인스턴스 간 잠금을 조정하는 중앙 메커니즘이 없어 경쟁 상태가 발생할 수 있으며, 인스턴스 장애 시 잠금이 해제되지 않을 수 있다. |
| 2 | 데이터베이스 트랜잭션을 이용해 운전자의 상태를 outstanding_request로 변경하여 중복 요청을 방지한다. 수락 시 accepted, 거절 시 available로 변경하고, 타임아웃 시 잠금을 해제한다. 하지만 인메모리 타이머는 서비스 장애 시 유실될 수 있어 잠금이 무기한 유지될 위험이 있다. |
| 3 | Redis의 분산 락과 TTL을 활용해 운전자별 잠금을 관리한다. 잠금 획득에 성공한 인스턴스만 호출 요청을 보내며, 수락 시 데이터베이스 상태를 accepted로 변경하고 잠금을 해제한다. 응답이 없으면 TTL에 의해 자동 만료된다. 대신 Redis의 가용성에 의존하므로 장애 조치와 모니터링이 필요하다. |

## NFR-3. High Throughput

요구 수준
`throughput` — 시스템은 특히 피크 시간이나 특별 이벤트에서 높은 처리량을 감당해야 한다(동일 위치에서 10만 건의 요청이 발생하는 상황).

### C3. 대규모 위치 업데이트 처리 · 15

평가 항목
위치 정확도를 유지하면서 빈번한 운전자 위치 업데이트로 발생하는 시스템 과부하를 어떻게 관리할 것인가?

| Level | 기준 |
|---|---|
| 0 | 위치 정확도를 유지하면서 빈번한 운전자 위치 업데이트로 발생하는 시스템 과부하를 어떻게 관리할지 고민하지 않는다. |
| 1 | 운전자의 위치 업데이트를 처리하는 서버를 수평 확장하여 처리량을 늘린다. 하지만 위치 업데이트 발생량 자체는 줄이지 못하므로 운전자 수가 증가할수록 데이터베이스 등의 하위 시스템에 병목이 발생하거나 운영 비용이 증가할 수 있다. |
| 2 | 운전자의 위치가 일정 거리 이상 변경되었을 때만 업데이트하여 불필요한 전송을 줄인다. 하지만 고정된 거리 기준만 사용하므로 운전자의 이동 방향이나 호출 요청 상황 등에 따라 요구되는 위치 정확도를 유연하게 반영하기 어렵다. |
| 3 | 운전자의 속도, 이동 방향, 상태 등에 따라 위치 업데이트 주기를 동적으로 조정한다. 정지하거나 느리게 이동할 때는 업데이트 빈도를 줄이고, 빠르게 이동하거나 방향을 자주 바꿀 때는 빈도를 높여 위치 정확도를 유지하면서 업데이트 처리량을 줄인다. 대신 최적의 업데이트 주기를 결정하는 알고리즘의 복잡성과 정확도 검증 비용이 발생한다는 사실을 인지한다. |

### C4. 피크 시간대 호출 요청 유실 방지 · 20

평가 항목
수요가 몰리는 시기에 차량 호출 요청이 하나도 유실되지 않도록 하려면 어떻게 해야 할까?

| Level | 기준 |
|---|---|
| 0 | 수요가 몰리는 시기에 차량 호출 요청이 유실되지 않도록 하는 방법을 고민하지 않는다. |
| 1 | 큐 없이 차량 호출 요청을 도착하는 순서대로 처리하고, 부하 증가 시 차량 매칭 서비스를 수평 확장한다. 하지만 갑작스러운 수요 급증이나 서비스 장애 시 요청이 유실될 수 있으며, 이를 복구할 방법이 없다. |
| 2 | 내구성 있는 메시지 큐에 차량 호출 요청을 저장하고, 차량 매칭 서비스가 큐에서 요청을 가져와 처리한다. 요청 처리 완료 후 확인 응답을 보내도록 하여 서비스 장애 시에도 미처리 요청을 다시 처리할 수 있다. 하지만 매칭 서비스의 처리 용량이 고정되어 있어 갑작스러운 수요 급증 시 큐에 요청이 쌓이고 매칭 지연이 증가할 수 있다. |
| 3 | Kafka와 같은 분산 메시지 큐에 호출 요청을 저장하고, 매칭 처리 완료 후에만 오프셋을 커밋하여 서비스 장애 시에도 요청을 다시 처리할 수 있도록 한다. 큐의 크기에 따라 차량 매칭 서비스 인스턴스를 동적으로 확장하고, 필요하면 지역별로 큐를 분할한다. 대신 큐 관리의 복잡성과 FIFO 처리로 인한 대기 지연 문제가 발생할 수 있음을 설명한다. |
