# LeetCode 코딩 문제 풀이 및 채점

**설계 범위**
문제 목록·상세 조회, 여러 언어의 코드 제출, 격리 환경에서의 테스트 실행과 결과 반환, 대회 리더보드 조회까지 설계한다. 사용자 프로필·결제·문제 추천은 제외한다.

**평가 초점**
제출 코드의 격리 실행과 서비스 보호, 5초 이내 제출 결과 반환, 빈번한 리더보드 조회 최적화, 10만 명 규모 대회의 코드 제출 처리 확장

**대상 연차** Senior\

## NFR-1. High Availability

**요구 수준**
`availability` — 시스템은 신뢰할 수 없는 사용자 코드를 실행하더라도 API 서버와 다른 사용자의 정상적인 요청 처리가 중단되지 않도록 실행 환경을 격리하고 자원 사용을 제한해야 한다.

### C1. 제출 코드 격리 실행과 서비스 보호 · 35

**평가 항목**
사용자 코드의 격리·자원 제어 메커니즘과 남은 보안 경계의 한계 및 실행 환경 선택의 Trade-off를 평가한다.

| Level | 기준 |
| --- | --- |
| 0 | 사용자 코드가 API 서버나 다른 실행 환경에 영향을 줄 수 있다는 격리 문제를 고려하지 않는다. |
| 1 | 사용자 코드를 API 서버 프로세스에서 직접 실행하고 결과를 반환한다. 악성 코드나 자원 고갈로 API와 다른 제출이 영향을 받는 문제를 막지 못한다. |
| 2 | 사용자 코드를 API 서버와 분리된 VM에서 실행한다. 코드 디렉터리를 읽기 전용으로 두고 임시 출력 공간을 분리한다. CPU·메모리 상한, 타임아웃, 외부 네트워크 차단을 적용한다. |
| 3 | 2점에 더해, VM의 시작 지연·자원 비용을 줄일 컨테이너 실행을 검토한다. 컨테이너의 커널 공유 위험을 시스템 호출 제한 등으로 통제하고, 격리 강도·시작 시간·비용의 Trade-off를 정당화한다. |

## NFR-2. High Scalability

**요구 수준**
`scalability` — 시스템은 10만 명 규모의 대회에서 코드 제출이 순간적으로 증가해도 언어별 채점 작업을 분산하고 필요에 따라 실행 용량을 늘릴 수 있어야 한다.

### C2. 대규모 코드 제출 처리 확장 · 25

**평가 항목**
언어별 실행 워커의 동적 확장과 제출 급증에 대한 완충·복구 메커니즘, 응답 지연과 운영 복잡성의 Trade-off를 평가한다.

| Level | 기준 |
| --- | --- |
| 0 | 대규모 대회에서 제출이 몰릴 때 채점 실행 용량과 작업 적체를 어떻게 관리할지 고려하지 않는다. |
| 1 | 채점 서버의 CPU·메모리를 늘리는 수직 확장에 의존한다. 서버 한 대의 상한과 유휴 시간의 자원 낭비를 해결하지 못한다. |
| 2 | 언어별 격리 실행 워커를 수평 배치하고 CPU 사용률·대기 작업량 등을 기준으로 워커 수를 자동 조정한다. 제출을 가용 워커에 분산해 단일 서버 병목에 대응한다. |
| 3 | 2점에 더해, 급격한 제출 폭증에는 자동 확장만으로 부족할 수 있음을 분석한다. 큐로 작업을 완충하고 실패한 실행을 재시도할지 검토하며, 결과 지연·복구 이점·운영 복잡성의 Trade-off를 설명한다. |

## NFR-3. Low Latency

**요구 수준**
`latency` — 시스템은 제출된 코드의 테스트 결과를 5초 이내에 반환할 수 있도록 실행 환경 준비 시간과 채점 대기 시간을 줄여야 한다.

### C3. 코드 제출 결과 반환 지연 단축 · 20

**평가 항목**
언어별 실행 환경 재사용과 제출 결과 반환 경로의 지연 요인, 준비된 실행 자원과 시작 비용 간 Trade-off를 평가한다.

| Level | 기준 |
| --- | --- |
| 0 | 채점 결과를 5초 이내에 반환하기 위한 실행 시작 지연과 제출 대기 시간 문제를 고려하지 않는다. |
| 1 | 제출마다 별도 VM을 새로 실행해 채점 결과를 반환한다. 격리는 제공하지만 VM 시작 지연과 실행 환경 준비 비용을 줄이는 메커니즘이 없다. |
| 2 | 언어별 의존성이 준비된 컨테이너를 재사용하고, 가용한 실행 워커에 제출을 즉시 할당한다. 실행 타임아웃을 적용하고 제출부터 결과 저장·반환까지의 지연을 관리한다. |
| 3 | 2점에 더해, 미리 가동한 컨테이너가 부족하면 대기하고 많으면 유휴 비용이 생기는 한계를 분석한다. 사전 가동·필요 시 시작·서버리스 실행의 시작 지연·비용 Trade-off로 선택을 정당화한다. |

## NFR-4. High Throughput

**요구 수준**
`throughput` — 시스템은 대회 참가자가 수초 간격으로 리더보드를 반복 조회해도 매번 전체 제출 내역을 집계하지 않고 높은 조회 요청량을 감당해야 한다.

### C4. 대회 리더보드 조회 최적화 · 20

**평가 항목**
리더보드 집계·캐시 갱신 메커니즘과 점수 최신성, 조회 비용 간 Trade-off를 평가한다.

| Level | 기준 |
| --- | --- |
| 0 | 반복적인 리더보드 조회가 DB 집계와 정렬에 큰 부하를 줄 수 있다는 문제를 고려하지 않는다. |
| 1 | 조회 때마다 DB에서 참가자별 정답 수를 집계하고 순위를 정렬한다. 기능은 제공하지만, 대회 중 반복 조회에 따른 쿼리 비용과 병목을 해결하지 못한다. |
| 2 | 제출 결과 DB와 별도로 주기적으로 갱신되는 리더보드 캐시를 두고, 조회는 캐시의 상위 순위만 읽도록 한다. 전체 집계 부하를 줄이되 갱신 간격의 지연을 관리한다. |
| 3 | 2점에 더해, 주기적 캐시 갱신의 최신성 한계를 분석한다. 채점 완료 시 Redis Sorted Set 같은 정렬 구조를 증분 갱신하고, 실시간성·정합성 관리·운영 비용의 Trade-off를 설명한다. |
