# LeetCode 코딩 문제 풀이 및 채점

**설계 범위**
문제 목록·상세 조회, 여러 언어의 코드 제출, 격리 환경에서의 테스트 실행과 결과 반환, 대회 리더보드 조회까지 설계한다. 사용자 프로필·결제·문제 추천은 제외한다.

**평가 초점**
제출 코드의 격리 실행과 서비스 보호, 5초 이내 제출 결과 반환, 빈번한 리더보드 조회 최적화, 10만 명 규모 대회의 코드 제출 처리 확장

**대상 연차** Middle\

## NFR-1. High Availability

**요구 수준**
`availability` — 시스템은 신뢰할 수 없는 사용자 코드를 실행하더라도 API 서버와 다른 사용자의 정상적인 요청 처리가 중단되지 않도록 실행 환경을 격리하고 자원 사용을 제한해야 한다.

### C1. 제출 코드 격리 실행과 서비스 보호 · 35

**평가 항목**
사용자 제출 코드의 오류·악의적 동작이 채점 API와 다른 제출의 실행에 영향을 주지 않도록 하는 기본 설계를 평가한다.

| Level | 기준 |
| --- | --- |
| 0 | 사용자 코드를 실행할 때 서버나 다른 사용자가 영향을 받을 수 있다는 문제를 고려하지 않는다. |
| 1 | 제출 코드를 API 서버에서 직접 실행한다. 실행 결과는 반환하지만, 악성 코드나 무한 루프로 API 서버가 중단될 위험을 막지 못한다. |
| 2 | API 서버가 제출을 별도의 VM이나 컨테이너에 전달하고, 격리된 환경에서 실행한 결과만 반환하는 흐름을 설명한다. 사용자 코드 오류가 API 서버에 전파되지 않도록 한다. |
| 3 | 2점에 더해, 격리 환경에서도 무한 루프나 과도한 CPU·메모리 사용이 발생할 수 있음을 설명한다. 실행 시간과 자원 사용량에 제한을 두는 기본 개선 방안을 제시한다. |

## NFR-2. High Scalability

**요구 수준**
`scalability` — 시스템은 10만 명 규모의 대회에서 코드 제출이 순간적으로 증가해도 언어별 채점 작업을 분산하고 필요에 따라 실행 용량을 늘릴 수 있어야 한다.

### C2. 대규모 코드 제출 처리 확장 · 25

**평가 항목**
대회 중 몰리는 코드 제출을 여러 채점 실행 환경에 분산하고 처리 용량을 늘리는 기본 설계를 평가한다.

| Level | 기준 |
| --- | --- |
| 0 | 대회 중 제출이 급증할 때 채점 서버의 실행 용량이 부족해질 수 있다는 문제를 고려하지 않는다. |
| 1 | 제출량이 늘면 채점 서버의 CPU·메모리를 더 큰 사양으로 교체한다. 한 서버의 용량 한계 때문에 대규모 대회에 대응하기 어렵다. |
| 2 | 언어별 코드 실행 워커를 여러 개 두고 제출을 나누어 처리하는 흐름을 설명한다. 참가자 수가 증가하면 워커 수를 늘려 채점 작업을 분담한다. |
| 3 | 2점에 더해, 갑작스러운 제출 증가로 워커가 모두 바빠질 수 있다는 한계를 설명한다. 대기 큐에 작업을 보관하고 실행 가능한 워커가 순서대로 가져가도록 개선한다. |

## NFR-3. Low Latency

**요구 수준**
`latency` — 시스템은 제출된 코드의 테스트 결과를 5초 이내에 반환할 수 있도록 실행 환경 준비 시간과 채점 대기 시간을 줄여야 한다.

### C3. 코드 제출 결과 반환 지연 단축 · 20

**평가 항목**
코드 제출부터 테스트 실행과 결과 반환까지의 흐름에서 실행 환경 준비로 발생하는 지연을 줄이는 기본 설계를 평가한다.

| Level | 기준 |
| --- | --- |
| 0 | 코드를 제출한 뒤 채점 결과를 반환하기까지의 실행 시작 시간과 대기 지연을 고려하지 않는다. |
| 1 | 제출마다 새 VM을 실행해 코드를 채점하고 결과를 반환한다. 격리는 가능하지만 시작 시간이 길어져 결과 응답이 지연될 수 있다. |
| 2 | 언어별 실행 환경을 미리 준비해 재사용하고, API가 제출을 해당 실행 환경에 전달해 테스트 결과를 반환하는 흐름을 설명한다. 매 요청마다 환경을 새로 시작하는 시간을 줄인다. |
| 3 | 2점에 더해, 준비된 실행 환경이 모두 사용 중이면 제출이 대기해 응답이 늦어진다는 한계를 설명한다. 대기량에 따라 해당 언어의 실행 환경 수를 조절하는 개선 방안을 제시한다. |

## NFR-4. High Throughput

**요구 수준**
`throughput` — 시스템은 대회 참가자가 수초 간격으로 리더보드를 반복 조회해도 매번 전체 제출 내역을 집계하지 않고 높은 조회 요청량을 감당해야 한다.

### C4. 대회 리더보드 조회 최적화 · 20

**평가 항목**
대회 순위를 반복 조회할 때 집계 부하를 줄이고 빠르게 응답하는 기본 데이터 처리 흐름을 평가한다.

| Level | 기준 |
| --- | --- |
| 0 | 리더보드 요청마다 제출 데이터를 다시 계산할 때 발생하는 조회 지연을 고려하지 않는다. |
| 1 | 참가자가 리더보드를 조회할 때마다 DB에서 제출 기록을 집계·정렬한다. 참가자와 조회 요청이 늘어나면 DB 부하와 응답 지연이 커진다. |
| 2 | DB에서 리더보드를 주기적으로 집계해 캐시에 저장하고, 참가자에게는 캐시된 순위를 반환하는 기본 흐름을 설명한다. 매 요청의 전체 집계를 피한다. |
| 3 | 2점에 더해, 주기적 갱신만으로는 새 제출 결과가 순위에 늦게 반영될 수 있음을 설명한다. 채점 완료 시 캐시의 점수와 순위를 갱신하는 개선 방안을 제시한다. |
